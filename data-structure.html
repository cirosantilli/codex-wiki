Data structure

 Home Computer science
OurBigBook.com Words: 15k Articles: 95
A data structure organizes stored information together with operations for accessing and changing it. Choosing a data structure means choosing which questions should be cheap to answer: an array supports access by numbered position, a hash table supports lookup by key, and a priority queue supports selecting an item by priority. The operations and their time complexity matter as much as the stored values.
Suppose three requests arrive as (5,Ada),(2,Bo),(4,Cy), where the number is a priority and smaller numbers are more urgent. A FIFO queue removes Ada first because she arrived first. A minimum-oriented priority queue removes Bo first because 2 is the least priority. An array can store the same three records in arrival order, but finding the least priority by scanning this representation takes three key inspections. A binary heap organizes these records so the least priority is immediately available. The information is the same; the representation changes the work needed to use it.
This is a useful design principle: preserve just enough organization for the operations the application needs. Maintaining a sorted array gives the whole order, but moving entries to insert a new key can be expensive. A binary heap keeps a weaker heap order that supports fast repeated selection without maintaining a sorted array. A good data structure makes an algorithm's next step easy.

Suffix array (SA)

Data structure OurBigBook.com
A suffix array stores starting positions of a string's suffixes in lexicographic order. All suffixes starting with a fixed query occupy a consecutive interval. This permits string-searching algorithms to search a compact list of positions instead of storing every suffix explicitly.

A wavelet tree recursively partitions an alphabet and records bit sequences indicating which partition each character belongs to. A character rank query follows the relevant partitions while mapping the prefix length through the bit-sequence ranks. A balanced tree takes logarithmically many levels in the alphabet size.

Heap implementations provide one way to realize a priority queue; the abstract queue and its implementing structure are distinct concepts.

Adjacency list (Adj[v])

Words: 1k Articles: 3
Data structure OurBigBook.com
An adjacency list represents a graph by keeping, for each vertex v, a collection Adj[v] of the vertices reached by its outgoing edges. An array indexed by vertex identifiers can locate each collection; the collection itself may use a linked list or an array. In an undirected graph, each nonloop edge supplies an entry at both endpoints.[ref]
For a worked example, take the simple graph
V={A,B,C,D,E,F},E={AB,AC,BC,CD,DE,DF,EF},
(1)
where AB denotes the unordered pair {A,B}. Its adjacency lists, displayed in label order, are
Adj[A]Adj[D]​=(B,C),=(C,E,F),​Adj[B]Adj[E]​=(A,C),=(D,F),​Adj[C]Adj[F]​=(A,B,D),=(D,E).​
(2)
Thus C has three neighbours, although the graph has six vertices. Its list contains exactly the destinations available for a single step from C; no slots are reserved there for C,E,F. The fourteen neighbour entries represent seven edges, with CD appearing as D in C's list and as C in D's list. The label order makes the example easy to read; an adjacency list need not be sorted.
The useful idea is to store existing connections explicitly. Neighbour enumeration can then follow exactly the possible next steps, which is what breadth-first search and depth-first search need. In a sparse graph, most pairs of vertices have no edge; adjacency lists avoid reserving a separate adjacency matrix entry for every such absence. Whether this saves work depends on the question: neighbour enumeration and testing one proposed edge have different costs.

Adjacency list edge conventions

Words: 305
Adjacency list OurBigBook.com
For a directed graph, store v in Adj[u] for the edge u→v. The reverse edge v→u is separate and is stored only if it exists. Consequently, list length is outdegree, not indegree, and each directed edge contributes one entry in total. An incoming-list index is additional storage.[ref]
Orient the seven edges of our example from earlier to later labels. The resulting directed graph has
Adj[A]Adj[D]​=(B,C),=(E,F),​Adj[B]Adj[E]​=(C),=(F),​Adj[C]Adj[F]​=(D),=().​
(3)
There are now seven entries, with outdegrees (2,1,1,2,1,0). In particular, F needs an empty list even though it is reached from D,E: incoming edges do not make F's outgoing list nonempty. Replacing each directed edge by an undirected graph connection would lose this distinction.
Our running simple graph excludes self-loops and repeated edges. If those restrictions are relaxed, specify how the adjacency list encodes them. Here an undirected self-loop at u contributes two copies of u to Adj[u], matching its contribution of two to the degree of a vertex. A directed self-loop contributes one copy, and one each to outdegree and indegree. Distinct parallel edges retain distinct entries; a multigraph's list length can therefore exceed its number of distinct neighbours.[ref][ref]
For example, add one undirected self-loop at A to the seven-edge example. Its list becomes (B,C,A,A), the vertex degree of A becomes four, and the total entry count becomes sixteen for eight edges. If an application instead stores a self-loop once, it must account for its doubled undirected vertex degree separately. In a weighted graph, an entry can be an ordered pair (v,w) meaning destination v and weight w; the weight belongs to the edge, not to the destination vertex.

Neighbour enumeration

Words: 232
Adjacency list OurBigBook.com
Neighbour enumeration reports the neighbours of a specified vertex. For a simple graph, scan its adjacency list and report each entry. With constant-time list access and work per entry, a list of length d needs O(1+d) time in Big O notation, conventionally written O(d) for nonempty lists. Use vertex degree for an undirected graph and outdegree for a directed graph. Obtaining the list reference can take constant time; consuming it requires visiting every entry.[ref]
In our undirected example, enumerating C's neighbours reads A,B,D: three entries. Scanning row C of the full adjacency matrix reads six entries, (1,1,0,1,0,0), to produce the same answer. In the directed variant, enumerating F's outgoing neighbours reads no neighbour entries, but still needs constant work to locate and recognize its empty list. For a multigraph, scanning lists enumerates incident edges with multiplicity; reporting only distinct neighbours additionally requires removing repetitions.
For a short time complexity argument, each reported entry requires at least one output operation, and one scan suffices. Across all vertices, the undirected entry count is ∑v∈V​deg(v)=2∣E∣ by the handshaking lemma; the directed count is ∑v∈V​d+(v)=∣E∣. A graph search that processes each vertex once and scans each of its entries once therefore does O(∣V∣+∣E∣) structural work, provided its visited-state access and FIFO queue or stack operations also have the required constant-time costs. With a full adjacency matrix, scanning every row instead inspects ∣V∣2 entries. This is how the representation enters the analysis of breadth-first search and depth-first search.

Adjacency list storage and query costs

Words: 406
Adjacency list OurBigBook.com
Write n=∣V∣ and m=∣E∣. Suppose each vertex identifier, list descriptor, link and optional edge weight occupies a constant number of machine words, and indexed array access and identifier comparison take constant time. There are n list descriptors and m directed, or 2m undirected, neighbour entries. Hence adjacency lists use O(n+m) machine words in Big O notation. A full adjacency matrix has n2 entries, regardless of m. These are counts under a storage model, not fixed byte sizes.[ref]
Our undirected example has six list descriptors and fourteen neighbour entries, versus thirty-six full adjacency matrix entries. The numbers 20 and 36 count different kinds of logical items: they do not prove a particular byte saving. A linked list also needs links; an array may have unused capacity. Storing only half of a symmetric matrix changes its exact count while leaving quadratic growth. If identifiers or weights require growing numbers of machine words, their size must be included in the space complexity.
An unsorted adjacency list answers "does the edge u→v exist?" by linear search through Adj[u]. In the worst case it inspects all d entries, giving O(1+d) time, or O(d) for d≥1. Even if v is absent, an uninspected entry could still contain it, so arbitrary lists require the whole scan. On our example, looking for CF in C's list compares F with A,B,D and fails after three comparisons. A full adjacency matrix instead answers from its single C,F entry in O(1) time.[ref]
Different promises change the query. A sorted array of neighbour identifiers permits binary search in O(log(d+1)) time, but maintaining order after insertion may require shifting entries. A per-vertex hash table permits expected constant-time membership under the hashing and load assumptions of that data structure; it does not give that guarantee to an arbitrary adjacency list. A stored list length can likewise make a vertex degree query constant-time even though neighbour enumeration still has to visit its entries.
The advantage grows with scale. For a graph path on n≥2 vertices, m=n−1, so there are 2n−2 undirected neighbour entries and n descriptors, versus n2 full adjacency matrix entries. Such a family is a sparse graph with m=O(n). For a complete graph, m=n(n−1)/2, so the undirected neighbour entries already number n(n−1): the adjacency list advantage in growth rate disappears. Choose by the workload: following existing edges favours adjacency lists; many arbitrary pair-membership queries can favour a full adjacency matrix. The representation organizes the same graph for different questions.

Priority queue

Words: 1k Articles: 4
Data structure OurBigBook.com
A priority queue stores items with comparable priority keys and supports insertion, inspection of a best-priority item, and removal of a best-priority item. Here we use the minimum convention: keys have a total order, and smaller means earlier. The operation peek returns a stored item of minimum priority without removing it; extract-min removes and returns such an item. Both require a nonempty priority queue, or an explicitly specified empty-case result. A maximum-oriented priority queue reverses the choice.
For the requests (5,Ada),(2,Bo),(4,Cy), peek returns Bo and leaves all three requests stored. extract-min returns Bo and leaves Ada and Cy; another peek returns Cy. Inserting (1,Dee) now makes Dee the next request selected. This changing collection need not be a sorted array: only the next choice must be available.
Distinct items may share a priority. Inserting (2,Eli) alongside (2,Bo) permits either item to be removed first. A priority queue does not inherently promise arrival order on ties. If that policy matters, compare priority first and a unique increasing arrival number second; the resulting total order makes earlier arrivals win equal-priority ties. This is analogous to the motivation for stable sorting, but it is an extra policy for the priority queue.
The interface specifies behavior; the data structure determines costs. A binary heap implements a priority queue with constant-time peek and logarithmic-time insertion and extract-min, under the cost assumptions below. Scheduling by urgency or by the time of the next event needs exactly this repeated next-item selection. MIT's notes use these applications to motivate the priority queue interface.[ref]

Binary heap

Words: 997 Articles: 3
Priority queue OurBigBook.com
A binary heap represents a priority queue as a complete binary tree obeying a heap order. We use the minimum convention: the priority of every parent in a rooted tree is no greater than the priorities of its children in a rooted tree. Equal priorities are allowed. Each stored entry may be a record carrying a priority key; the numerical example below displays only keys. Reversing the inequalities gives the maximum convention.
The complete binary tree can be stored directly in a zero-indexed array A=(A0​,…,An−1​): read its levels from top to bottom, left to right. The root of a tree is at index 0. The possible children in a rooted tree of index i are at 2i+1 and 2i+2, and an index denotes a present entry only when it is less than n. For i>0, its parent in a rooted tree is at ⌊(i−1)/2⌋, using the floor function. Thus the links of the complete binary tree are determined by arithmetic rather than separately stored pointers.
Consider
A=(2,5,3,9,7,8,4).
(4)
The children in a rooted tree of index 0 have keys 5,3; those of index 1 have keys 9,7; those of index 2 have keys 8,4. The six comparisons 2≤5, 2≤3, 5≤9, 5≤7, 3≤8, 3≤4 establish the heap order. At index 4, the parent in a rooted tree is index ⌊(4−1)/2⌋=1, carrying key 5.
The array is visibly not a sorted array: 5 precedes 3, and 8 precedes 4. Nor is the last entry a maximum: it is 4, whereas the maximum is 9 at index 3. The heap order compares ancestors and descendants, without imposing an order between separate branches. Nevertheless, following the graph path from the root of a tree to any entry gives a chain of nondecreasing priorities. This short argument proves that peek can return A0​, a minimum, without inspecting the other entries.
Insertion appends an entry to the array, preserving the shape of the complete binary tree, then uses sift up to repair the heap order. Insert key 1 into the displayed binary heap. It is appended at index 7, and exchanges with indices 3, 1, then 0:
(2,5,3,9,7,8,4,1)​⟶(2,5,3,1,7,8,4,9)⟶(2,1,3,5,7,8,4,9)⟶(1,2,3,5,7,8,4,9).​
(5)
The moving key follows 7→3→1→0; the keys 9,5,2 each move down one level. Only this chain needs repair.
Now apply extract-min. Save key 1, move the last key 9 to the root of a tree, and shorten the array to length 7. Use sift down, always choosing the smaller of the present children in a rooted tree:
(9,2,3,5,7,8,4)​⟶(2,9,3,5,7,8,4)⟶(2,5,3,9,7,8,4).​
(6)
First 9 exchanges with key 2 at index 1, since 2<3; then with key 5 at index 3, since 5<7. At index 3, the possible children in a rooted tree would be indices 7,8, both outside the shortened array, so the process stops. The returned key is 1, and the remaining binary heap is exactly the original one.
For a nonempty binary heap with n entries, the deepest level is ⌊log2​n⌋, using the floor function and logarithm. Each exchange moves one level and uses only a bounded number of comparisons. The resulting time complexity bounds, expressed in Big O notation, are:
OperationTime complexityReason
peekO(1)Read the root of a tree.
InsertO(logn) for n≥2Append, then sift up through at most the levels of the complete binary tree.
extract-minO(logn) for n≥2Move the last entry, then sift down through at most those levels.
Build from an arbitrary arrayO(n)Apply sift down from the last index with children in a rooted tree back to index 0.
These bounds assume constant-cost indexed access, key comparisons and exchanges, and available array capacity for insertion. Allocating and copying a larger array is a separate cost. Empty and one-entry cases take constant work.
To build a binary heap, begin at index ⌊n/2⌋−1 and work backwards. Entries without children in a rooted tree already obey the heap order. Each sift down, also called heapify down, starts with every present smaller rooted tree below it already repaired. Most entries are close to the bottom and can move very little; successively longer repair distances occur for geometrically fewer entries. Summing these distances gives O(n) work, rather than charging O(logn) to every entry. MIT's notes give this bottom-up construction and contrast it with repeated insertion.[ref]
The Dijkstra algorithm additionally needs to decrease the priority of an existing vertex when its tentative distance improves. Given its current index, lowering the key followed by sift up takes O(logn) time for n≥2. An indexed binary heap maintains a separate map from item identity to its current index and updates that map after every exchange. For vertices numbered in a fixed range, the map can be another array, giving constant-time index lookup. An ordinary unindexed binary heap supplies no such guarantee: locating an arbitrary item can require scanning n entries. Item identity and priority must remain distinct, especially when several vertices have equal tentative distances.
The attractive compromise is local organization with global usefulness. A binary heap maintains only the heap order, yet every extract-min gives the next smallest key. Repeated extraction of the original example gives 2,3,4,5,7,8,9, so a priority queue also supplies a sorting algorithm without storing a sorted array between extractions.

Sift up

Binary heap OurBigBook.com
After inserting or lowering a key in a minimum-oriented binary heap, compare it with its parent in a rooted tree. Exchange them while the moving key is smaller, then continue at its new index. Stop at the root of a tree or when the heap order is satisfied. This repair assumes the rest of the binary heap was valid before the insertion or key decrease.

Sift down

Words: 63
Binary heap OurBigBook.com
To repair a key in a minimum-oriented binary heap, choose the smaller-priority present entry among its children in a rooted tree. Exchange if that entry is smaller than the moving key, and continue at the new index. Stop when there are no children in a rooted tree or the heap order holds. The smaller rooted trees below the starting entry must already obey the heap order; choosing the larger child could leave a violation with the smaller one.

Hash table

Words: 4k Articles: 16
Data structure OurBigBook.com
A hash table stores records by key: for example, a product number can select its current stock count without scanning every product. A hash function selects a hash bucket in an array, and a collision-handling method such as separate chaining retains distinct keys assigned to the same hash bucket. The useful idea is to narrow the search to one small collection, while key equality decides which record actually matches.
Use a map interface with one value per key: get(k) returns the associated value or an explicit absent result; put(k,v) replaces the value if an equal key is present, otherwise inserts a new record; delete(k) removes the matching record if present. The absent result must be distinguishable from every permitted stored value. Replacing a value does not increase the record count n. A hash collision between unequal keys must never cause one record to replace the other.[ref]
Let x∼y denote the chosen key equality, an equivalence relation, and let hm​ be the bucket-index hash function for m>0 hash buckets. Correctness requires
x∼y ⟹ hm​(x)=hm​(y),hm​(x)∈{0,…,m−1}.
(7)
The converse is false: equal bucket indices merely identify candidates for a key equality comparison. If an implementation first computes a full hash value H(k) and then reduces it to a bucket index, equal keys must have equal H values too. Keep both key equality and the hash function stable while a key is stored; changing the key so it selects another hash bucket can make its record unreachable. This distinction is explicit in the published hashCode/equals contract.[ref]
For a constructed integer example, use modular arithmetic to define hm​(k)=kmodm and store keys 1,5,9,2 with values A,B,C,D. At m=4, three records share hash bucket 1 and one occupies hash bucket 2. The hash table load factor is
α=mn​=44​=1.
(8)
It is the mean number of records per hash bucket, including empty hash buckets, not a bound on the longest chain. With separate chaining, α may exceed 1 because records live in the chains rather than one record being confined to each array slot.
Growing this example to m=8 changes the bucket-index hash function: key 5 now belongs to hash bucket 5, while keys 1,9 still share hash bucket 1. Every record must be assigned using the new bucket-index hash function; copying the old array of chain heads unchanged is insufficient. The hash table load factor becomes 4/8=1/2.
For an insertion-only sequence starting empty with constant initial capacity, one policy doubles m before inserting a new key that would make n>m. A rebuild for separate chaining allocates the new array and transfers each existing record directly into its new chain. Since keys are already distinct, transfer needs no duplicate search. With constant-cost hashing and linking, this takes O(n+m) time complexity, hence O(n) at a growth threshold. Amortized analysis charges the occasional rebuild across many insertions: the old capacities 1,2,4,…,2r form a geometric series with sum 2r+1−1, so total rebuilding work over N insertions is O(N). This gives O(1) amortized resizing overhead; an insertion that triggers a rebuild can still take O(n).[ref]
The search to check for an existing key is additional work. Bounded hash table load factor together with the probabilistic assumptions in separate chaining gives expected amortized O(1) insertion, not worst-case O(1). If the two disjoint-set representatives agree, no merge is needed. Here unite returns True exactly when it merges two different blocks of a set partition. A successful call decreases their count by one; a redundant call preserves it. The name union is also customary. Some interfaces instead accept already found disjoint-set representatives, making that linking step a separate operation.
For an original example, initialize X={1,2,3,4,5,6,7} as seven singleton sets. Apply the calls in this order:
unite(2,1), unite(4,3), unite(2,4), unite(6,5), unite(2,6), unite(1,2).
(24)
The first five calls succeed. After the third, the partition of a set is {{1,2,3,4},{5},{6},{7}}; after the fifth it is {{1,2,3,4,5,6},{7}}. The sixth returns False: 1,2 are already together. The blocks of a set partition number 7,6,5,4,3,2,2, counting the initial state. A disjoint-set find operation on 7 cannot merge it with any other member.
This is exactly the kind of changing membership needed by Kruskal component merging: an accepted edge joins two current connected components of a graph, while an edge whose endpoints already have equal disjoint-set representatives is rejected. The existing Kruskal's algorithm worked example follows that application. A disjoint-set forest stores membership efficiently without repeatedly enumerating every block of a set partition.

Disjoint-set forest

Words: 756 Articles: 2
Disjoint-set data structure OurBigBook.com
A disjoint-set forest represents each block of a set partition by a rooted tree. Each set element stores a pointer to its parent in a rooted tree; the root of a tree stores a pointer to itself as a stopping convention. These self-pointers are sentinels, omitted from the forest's edges. Following parent pointers reaches the disjoint-set representative, the root of a tree. An indexed array parent suffices when members are numbered consecutively. The rooted trees encode membership; their edges need not be edges of any input graph.
To link different blocks of a set partition, point one root of a tree at the other root of a tree. Linking roots preserves every old membership and joins exactly the two rooted trees. Arbitrarily reparenting a nonroot could detach only part of a block of a set partition, so it would not implement the required disjoint-set union operation. The disjoint-set find operation terminates because each nonroot pointer moves towards the unique root of a tree; linking distinct roots cannot introduce a graph cycle.

Union by rank (rank(r))

Disjoint-set forest OurBigBook.com
Union by rank keeps a nonnegative integer rank, initially zero, for each member. For each input, obtain its root of a tree using the disjoint-set find operation, then compare the resulting ranks. Attach the lower-rank root of a tree below the higher-rank root of a tree, leaving both ranks unchanged. When the two disjoint-set representatives differ but their ranks are equal, choose either survivor and increase its rank by exactly one. A redundant disjoint-set union operation changes no ranks. Path compression also changes no ranks. The surviving root's rank bounds the height of its rooted tree, measured in edges; after path compression it need not equal that height.[ref]
In our example, let the first argument's root of a tree survive equal-rank ties. The first two merges create roots 2,4, each of rank 1. The third gives parent[4]=2 and increases the rank of 2 to 2. The fourth creates root 6 of rank 1. The fifth attaches 6 below 2 without increasing any rank. Before any subsequent compression queries, the indexed arrays are

Two short arguments explain the rank invariant. First, a root of rank r has at least 2r members in its block of a set partition: rank zero starts with one, and increasing rank combines two disjoint blocks of a set partition with at least 2r members each. Unequal-rank linking only adds members. Thus every rank is at most ⌊log2​n⌋ for n stored members, using the floor function and logarithm. Second, height is initially zero; unequal-rank linking adds at most one to the lower height, while equal-rank linking raises the available bound by one. Path compression only shortens routes. These arguments prove a height bound, not the stronger amortized analysis below.

Path compression

Words: 343
Disjoint-set forest OurBigBook.com
Path compression changes parent pointers during a disjoint-set find operation so that future queries traverse fewer edges. Full path compression first follows the entire parent route to its root of a tree, then makes every member on that route point directly to that same root of a tree. No member changes its block of a set partition or its disjoint-set representative. Pointers outside the traversed route stay as they were. The following iterative Python implements full path compression and union by rank; parent and rank are initially indexed arrays with parent[x] = x and rank[x] = 0 for every valid member.
def find(x):
    root = x
    while parent[root] != root:
        root = parent[root]
    while parent[x] != x:
        following = parent[x]
        parent[x] = root
        x = following
    return root

def unite(x, y):
    a, b = find(x), find(y)
    if a == b:
        return False
    if rank[a] < rank[b]:
        a, b = b, a
    parent[b] = a
    if rank[a] == rank[b]:
        rank[a] += 1
    return True
Starting from the displayed disjoint-set forest, find(3) traverses 3→4→2, returns 2 and changes only parent[3] from 4 to 2. The route 5→6→2 still has two edges. Then find(5) changes only parent[5] from 6 to 2. The final parent array is (2,2,2,2,2,2,7); every stored rank retains its displayed value. The rooted tree at 2 now has height one although its root's rank is two. Root 7 still represents a separate singleton set.
The two-pass algorithm first discovers the answer and then reuses it. During the second pass, saving following before overwriting the pointer preserves the remaining route. Every replacement pointer targets the original root of a tree, proving that the partition of a set is unchanged.
Full path compression is one specific rule. The authored UF.java implementation instead uses path halving, redirecting a visited member to its parent's parent while advancing along the route. Its union by rank rule agrees with the one above.[ref]

Union-find operation bounds (O(n+mα(n)))

Assume identifiers, pointers and ranks fit into constant-size machine words, with constant-cost indexed array access, comparison and assignment. Initializing n≥1 members costs O(n) time and machine words. With union by rank and full path compression, any sequence of m disjoint-set find operations and disjoint-set union operations then has total time complexity, in Big O notation,
O(n+mα(n)).
(26)
Here α(n)≥1 is a conventionally normalized inverse Ackermann function. The documented path-halving implementation has the same amortized analysis bound.[ref]
A disjoint-set union operation includes two disjoint-set find operations and a constant amount of additional linking work. Including n in the bound accounts for initialization even if no queries follow.
This is a bound on an entire sequence. It is not a worst-case constant bound for each call: a disjoint-set find operation can still encounter a previously uncompressed route of logarithmic length. The inverse Ackermann function grows extraordinarily slowly but is unbounded, so it cannot be replaced by a mathematical constant in this asymptotic statement. The general distinction between a per-operation maximum and a whole-sequence guarantee is explained in amortized analysis.
Robert Tarjan's 1975 paper established an inverse Ackermann function bound for set union. Its abstract states the sharper two-parameter form for m≥n representative queries and n−1 intermixed merges: the worst total cost is bounded above and below by positive constant multiples of mα(m,n). Those variables count different operations from the convenient n+mα(n) formulation above; the abstract's matching lower bound is about its analyzed method, rather than a claim that every conceivable representation obeys the same lower bound.[ref]
The intuition is that union by rank limits how parent routes grow, while path compression makes an expensive traversal improve later queries. The rank argument alone proves only a logarithmic bound. Establishing the inverse Ackermann function bound requires a finer accounting of traversals across rank ranges; it does not follow merely from drawing a flatter rooted tree. The useful result is that repeated merging and membership queries can share the work of maintaining a changing partition of a set.
