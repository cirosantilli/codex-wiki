Separate chaining

 Home Computer science Data structure Hash table
OurBigBook.com Words: 626 Articles: 1
With separate chaining, each hash bucket in a hash table contains a collection of records, often a linked list. Lookup computes the bucket index, then follows that chain until a key equality comparison succeeds or the chain ends. A hash collision therefore affects the search work without merging unequal keys. Deletion searches the same chain and unlinks the matching record; in a singly linked list, remembering the preceding record during the search permits the unlink.[ref]
For the four-key integer example in hash table, insert a new record at the head of its chain after checking that its key is absent. Inserting (1,A),(5,B),(9,C),(2,D) in that order makes hash bucket 1 hold (9,C)→(5,B)→(1,A), hash bucket 2 hold (2,D), and the other two hash buckets empty. All five subsequent operations below select hash bucket 1 because 5mod4=13mod4=9mod4=1:
get(5) rejects key 9, accepts key 5, and returns B after two key equality comparisons. get(13) rejects 9,5,1 and reports absence after three comparisons. put(5,B*) examines 9,5 and replaces the value without changing n=4. delete(9) examines just the head record, removes it, and gives n=3. Finally, put(13,E) rejects 5,1 before inserting the new head record; n returns to 4 and the chain is (13,E)→(5,B∗)→(1,A). The successive hash table load factors are 1,1,1,3/4,1. These counts follow from the stipulated chain order; a different insertion policy changes the successful-search counts.
For a chain of length ℓ, lookup and deletion by key take O(1+ℓ) time complexity in Big O notation. The same applies to put before any resizing, since replacement semantics require checking for an existing equal key. Head insertion alone is O(1) if absence is already known; that is a different precondition. These bounds assume O(1) bucket-index hashing, array access, key equality comparisons, allocation and link updates. A long string or large integer can make hashing or comparison depend on its encoded length, so counting record visits alone does not establish constant running time.
Under simple uniform hashing, each distinct key's bucket index is an independent random variable with a uniform distribution on a finite set of m indices. The keys and query are fixed independently of this random assignment. Then lookup has expected O(1+α) time complexity, where α=n/m is the hash table load factor; it is expected O(1) when α stays bounded. These are model assumptions, not an automatic consequence of using a deterministic hash function.[ref]

by linearity of expectation. For a present fixed query, scanning its entire chain inspects at most itself plus all other colliding records, with expected value 1+(n−1)/m; stopping at the match only decreases this upper bound. Adding constant hashing and bucket access yields expected O(1+α) for either query. The argument needs pairwise collision bounds; it does not require all the indicator random variables to be independent. A universal hash family can provide a related bound by random choice of a hash function for a fixed key set, as explained in that article.
The worst case remains O(n), and an absent query takes n comparisons if all n records occupy its hash bucket. For instance, 1,1+m,1+2m,…,1+(n−1)m all collide under hm​(k)=kmodm. Separate chaining remains correct, but a sequence of insertions that each checks the existing chain can take quadratic total work. Amortized analysis of resizing does not remove this search cost, and an adaptive choice of keys based on a known hash function is outside the stated simple uniform hashing model.
