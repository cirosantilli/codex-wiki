= Computer network

A <computer network> connects computing devices so they can exchange data using <communication protocols>. <Packet switching> shares communication links among many exchanges; <routers> forward <network packets> between connected networks. The arrangement of machines and links need not coincide with the arrangement of administrative control.

= Ring network
{parent=Computer network}
{wiki}

A <computer network> with nodes connected around a cycle. A unidirectional <ring network> permits messages to move only in the chosen direction.

= Unicast
{parent=Computer network}
{wiki}

<Unicast> addresses a transmission to a single destination, in contrast with group-addressed <multicast> delivery.

= Multicast
{parent=Computer network}
{wiki}

<Multicast> delivers data to a group of interested receivers. A <multicast distribution tree> can share transmissions over common links and copy them where routes branch.

= Line code
{parent=Computer network}
{wiki}

= Line coding
{synonym}

A <line code> maps data to a sequence of physical signal levels or transitions for transmission. Timing, polarity and the length of runs of equal levels affect the choice.

= Block code for line coding
{parent=Line code}

A <block code for line coding> maps fixed-size groups of data <bits> to fixed-size transmitted <codewords>, chosen to meet signal constraints as well as to distinguish inputs. Constraints on long runs must also be checked across word boundaries.

= Differential Manchester encoding
{parent=Line code}
{wiki}

<Differential Manchester encoding> has a transition at every <bit> midpoint and encodes the data by the presence or absence of a boundary transition. A consistent signal polarity reversal preserves those transition decisions.

= Manchester code
{parent=Line code}
{c}
{wiki}

= Manchester encoding
{c}
{synonym}

<Manchester encoding> represents each data <bit> by two opposite half-bit levels. The compulsory midpoint transition supports <clock recovery>.

= Clock recovery
{parent=Line code}
{wiki}

<Clock recovery> extracts a timing reference from a received signal so that a receiver can locate symbol boundaries.

= Symbol rate
{parent=Computer network}
{title2=$R_s$}
{wiki}

= Baud rate
{synonym}

The <symbol rate>, measured in baud, counts signal elements per second. Its relation to <bit rate> depends on the representation and on which signal element is counted as a symbol.

= Bit rate
{parent=Computer network}
{title2=$R_b$}
{wiki}

The <bit rate> counts transmitted data <bits> per unit time. State which representation is being counted: payload <bits> and encoded link <bits> need not have the same rate.

= Network latency
{parent=Computer network}

<Network latency> is the delay associated with communication over a network, distinguished from the rate at which data can be transferred. Moving a delivery <endpoint> closer to demand can reduce some path delay, but does not by itself establish application correctness or independent control.

= Round-trip time
{parent=Network latency}
{title2=RTT}

The <round-trip time> measures the elapsed time for an exchange to travel to a peer and for a response to return. Feedback-based sending can be limited by this delay as well as by link capacity.

= Router
{parent=Computer network}

A <router> forwards <network packets> between networks using forwarding information. Ordinary <Internet Protocol> forwarding is distinct from a <middlebox> function that translates addresses, terminates a transport connection or applies an application-specific transformation.

= Packet switching
{parent=Computer network}

<Packet switching> carries separately represented units of data over shared communication links. Different <packets> can share forwarding resources; the network service need not reserve one dedicated circuit for an entire application exchange.

= Network packet
{parent=Packet switching}

= Packet
{synonym}

A <network packet> carries a unit of data together with <protocol> information used to interpret or deliver it. <Internet Protocol> carries datagrams; transport and application messages can span several such <packets>.

= Layered network architecture
{parent=Computer network}

A <layered network architecture> separates responsibilities behind communication interfaces. A <transport protocol> can offer an application a service built over <Internet Protocol> without requiring each underlying network to implement that application. Layer boundaries are engineering choices: the <end-to-end principle> helps assess which properties a lower layer can actually establish.

= Data link layer
{parent=Layered network architecture}
{wiki}

The <data link layer> organizes communication over a link, typically using <data-link frames> and local checking or access rules.

= Framing
{parent=Data link layer}

<Framing> identifies the boundaries of <data-link frames> in a transmitted stream, allowing a receiver to locate separately interpretable link-level units.

= Bit stuffing
{parent=Framing}
{wiki}

<Bit stuffing> inserts extra <bits> according to an agreed rule, for example after five consecutive ones, so that a reserved <frame delimiter> cannot occur inside encoded contents. The receiver reverses the insertion rule.

= Frame delimiter
{parent=Framing}

A <frame delimiter> marks a <data-link frame> boundary. A transparency rule such as <bit stuffing> prevents data from accidentally imitating the reserved delimiter.

= Frame
{disambiguate=networking}
{parent=Data link layer}
{wiki}

= Data-link frame
{synonym}

A <data-link frame> is a delimited unit of link-level transmission containing data and any associated control or checking fields.

= Transport protocol
{parent=Layered network architecture}

A <transport protocol> provides communication services between its transport <endpoints> over an underlying network. <Transmission Control Protocol> supplies a reliable ordered byte stream; <User Datagram Protocol> supplies datagrams without that built-in recovery service. Applications can implement further mechanisms over either interface.

= Flow control
{parent=Transport protocol}

<Flow control> limits a sender according to a receiver's buffering or processing capacity, rather than the capacity of the intervening <computer network>.

= Backpressure
{parent=Flow control}

A dependency by which an unready receiver delays upstream acceptance of further work. In <synchronous message passing> it can propagate through a chain of blocked sends; a finite buffer postpones this propagation until its capacity is used.

= Sliding window protocol
{parent=Transport protocol}
{wiki}

A <sliding window protocol> permits a range of numbered data to be outstanding or accepted, advancing that range as transmission makes progress.

= Receive window
{parent=Sliding window protocol}
{title2=$\mathrm{rwnd}$}

A <receive window> bounds the numbered data a receiver is prepared to accept. In <TCP>, the receiver advertises a window that limits the sender independently of the sender's <congestion window>.

= Send window
{parent=Sliding window protocol}
{title2=$W_s$}

A <send window> specifies the numbered data a sender may transmit before further progress permits the range to advance.

= Acknowledgement
{parent=Transport protocol}

= Acknowledgment
{synonym}

An <acknowledgement> reports receipt according to the <protocol>'s rules. A <TCP> cumulative <acknowledgement> names the next expected <byte>; it does not establish that the application has durably acted on all preceding data.

= Delayed acknowledgement
{parent=Acknowledgement}

A <delayed acknowledgement> postpones a response briefly so that one <acknowledgement> may cover more data or accompany returning data. Its timer can interact with <Nagle's algorithm> to delay a short exchange.

= Transport sequence number
{parent=Transport protocol}

A <transport sequence number> identifies a data position within an exchange, supporting ordering, duplicate rejection and precise <acknowledgements>. <TCP> numbers <bytes> rather than simply numbering <packets>.

= Retransmission
{disambiguate=data networks}
{parent=Transport protocol}
{wiki}

= Data retransmission
{synonym}

<Data retransmission> sends data again to recover from loss or detected corruption. <Transport sequence numbers> let a receiver recognize a duplicate if the original transmission arrived but its <acknowledgement> was lost.

= Transport port
{parent=Transport protocol}

A <transport port> is a numbered identifier used by a <transport protocol> to distinguish communication <endpoints> at a host. <TCP> and <UDP> have separate port spaces.

= QUIC
{parent=Transport protocol}
{c}

<QUIC> is a <transport protocol> designed over <User Datagram Protocol> with multiple streams and cryptographic protection. At the 17 January 2020 examination date, the cited November 2019 design was an Internet-Draft and work in progress. This historical description does not treat a later standard as already available.<QUIC: A UDP-Based Multiplexed and Secure Transport (Internet-Draft 24)>[4 November 2019, §1 and Status of This Memo]{ref}

= User Datagram Protocol
{parent=Transport protocol}
{c}

= UDP
{synonym}
{c}

<User Datagram Protocol> supplies a datagram transport interface without built-in reliable ordered-stream delivery. An application or another <protocol> can add recovery over that interface, as the pre-2020 <QUIC> design illustrates.

= Transmission Control Protocol
{parent=Transport protocol}
{c}

= TCP
{synonym}
{c}

<Transmission Control Protocol> provides a reliable ordered byte-stream service between its <endpoints>, using sequencing, acknowledgements and retransmission. Receipt by that transport does not establish that a receiving application has durably stored the data or completed a user operation.<Transmission Control Protocol (RFC 793)>[§§1.5 and 2.6: operation and reliable communication]{ref}

= Zero-window probe
{parent=Transmission Control Protocol}

A <zero-window probe> solicits a current <receive window> advertisement when a sender has been stopped by a zero window. Repeated probes recover from a lost reopening <acknowledgement>.

= Persist timer
{parent=Zero-window probe}

The <persist timer> schedules repeated <zero-window probes>, preventing an exchange from waiting forever after a window-reopening message is lost.

= Silly window syndrome
{parent=Transmission Control Protocol}
{wiki}

<Silly window syndrome> is inefficient transmission in tiny <TCP segments>, arising through small writes or small increments of advertised receiving space. Sender and receiver measures address different causes.

= Nagle's algorithm
{parent=Silly window syndrome}
{c}
{wiki}

<Nagle's algorithm> coalesces small writes while data are unacknowledged, permitting another send when a full <TCP segment> can be formed or the outstanding data have been acknowledged. It reduces tiny transmissions but can add delay.

= TCP segment
{parent=Transmission Control Protocol}
{c}

A <TCP segment> contains a <TCP> header and zero or more data <bytes>. The header carries sequencing, <acknowledgement> and <receive window> information.

= Internet
{parent=Computer network}
{c}

The <Internet> interconnects independently operated <computer networks> using the <Internet Protocol> suite. Its common inter-network interface supports diverse underlying networks and applications; individual services can still depend on centrally controlled providers.

= Content delivery network
{parent=Internet}

= CDN
{synonym}
{c}

A <content delivery network> uses delivery infrastructure, often at multiple locations, to supply content and direct requests to suitable delivery <endpoints>. It can retain objects through <caching> or retrieve them from an origin. Distribution across sites does not imply that those sites have independent administrative control.<Framework for Content Distribution Network Interconnection (RFC 7336)>[§1.2 and §2.1: reference model and request redirection]{ref}

= CDN edge
{parent=Content delivery network}
{c}

= Content delivery edge
{synonym}

A <CDN edge> is a delivery <endpoint> of a <content delivery network>. It may use <caching> or fetch content, and a provider can authorise it to terminate a <client> connection. Its location near demand and its administrative authority are separate properties.

= Domain Name System
{parent=Internet}
{c}

= DNS
{synonym}
{c}

The <Domain Name System> provides a hierarchical namespace with delegated administration and distributed <servers>. Caching and replication help supply its service. A consistent namespace is compatible with distribution of responsibility across organisations.<Domain Names - Concepts and Facilities (RFC 1034)>[§2.2, §3 and §4.2: goals, namespace and zones]{ref}

= Internet Protocol
{parent=Internet}
{c}

= IP
{synonym}
{c}

<Internet Protocol> supplies an inter-network datagram interface. Its basic <packet> delivery does not itself guarantee arrival, order, absence of duplicates or completion of an application operation. <IPv4> and <IPv6> are versions of this network-layer <protocol>.

= IP multicast
{parent=Internet Protocol}
{c}
{wiki}

<IP multicast> sends an <Internet Protocol> datagram to a group identified by a multicast <IP address>. Delivery retains the underlying best-effort nature of <Internet Protocol>.

= Multicast routing
{parent=IP multicast}

<Multicast routing> establishes and maintains the forwarding decisions that deliver group-addressed <packets> to interested receivers.

= Reverse path forwarding
{parent=Multicast routing}
{wiki}

<Reverse path forwarding> accepts a source's <multicast> traffic only on the interface selected for the reverse route to that source. With consistent loop-free routing, those parent choices define a source-rooted <tree>. Membership pruning can then remove unneeded branches.

= Multicast distribution tree
{parent=Multicast routing}

A <multicast distribution tree> describes the parent and outgoing branches used to distribute <packets> to a group. Source-rooted and shared-group designs make different state and path choices.

= IPv6
{parent=Internet Protocol}
{c}

<IPv6> uses 128-bit addresses and a revised <packet> format. More address space does not remove <firewalls> or decide which application providers must be trusted.<Internet Protocol, Version 6 (IPv6) Specification (RFC 8200)>[§1: expanded addressing and other protocol changes]{ref}

= IPv4
{parent=Internet Protocol}
{c}

<IPv4> uses 32-bit addresses. Address sharing through <network address and port translation> is one response to pressure on its globally usable address space.

= IP address
{parent=Internet Protocol}
{c}

An <IP address> identifies an interface or destination according to the relevant <Internet Protocol> addressing rules. It is not inherently the identity of a person, and address translation can change the address visible across a boundary.

= Internet architecture
{parent=Internet}

The <Internet architecture> comprises its <protocol> interfaces, addressing and naming arrangements, placement of functions and assumptions about communication. Physical connectivity, administrative control and application trust are distinct dimensions of this architecture.<Architectural Principles of the Internet (RFC 1958)>[§§2–3: internetwork layer and design issues]{ref}

= Internet service federation
{parent=Internet architecture}

= Federated network service
{synonym}

<Internet service federation> permits independently administered services to communicate through agreed <protocols>. <Internet> mail is an example: separate domains can exchange messages without every user joining one provider. Federation differs from placing many replicas behind one mandatory account authority, and it does not itself establish <cryptographic confidentiality> or freedom from software failures.<Simple Mail Transfer Protocol (RFC 5321)>[§§2.1–2.3: communication model and domain-based delivery]{ref}

= Middlebox
{parent=Internet architecture}

A <middlebox> performs a function on a communication path beyond ordinary <Internet Protocol> forwarding, such as address translation, traffic filtering or proxying. The function can be embedded in a device rather than implemented in a separate physical box. Its state and assumptions can affect failure recovery and <protocol> evolution.<Middleboxes: Taxonomy and Issues (RFC 3234)>[§1.1 and §4: definition and architectural issues]{ref}

= Proxy server
{parent=Middlebox}

= Application proxy
{synonym}

A <proxy server> performs communication operations on behalf of another participant. Whether it can inspect plaintext depends on the <protocols> and keys it uses: relaying opaque encrypted bytes differs from authorised <TLS termination>.

= Firewall
{parent=Middlebox}

A <firewall> enforces a communication policy, for example by filtering <packets> or tracking permitted exchanges. Blocking unwanted incoming traffic is a policy decision; it is not the definition of <network address translation>.

= Network address translation
{parent=Middlebox}
{title2=NAT}

<Network address translation> maps <IP addresses> between address realms. State and path constraints can affect sessions. <Network address and port translation> additionally maps transport ports. Translation does not itself require decryption of application payloads.<Traditional IP Network Address Translator (Traditional NAT) (RFC 3022)>[Abstract and §§1–2: address and port translation, state and limitations]{ref}

= Network address and port translation
{parent=Network address translation}
{title2=NAPT}

<Network address and port translation> permits several internal addresses and transport ports to share an external address by maintaining distinct translated bindings. Losing a binding can disrupt an exchange even when the application <endpoints> retain their own state.

= Port forwarding
{parent=Network address and port translation}
{wiki}

<Port forwarding> configures a mapping from an external <transport port> to an internal service, allowing selected inbound traffic through a translator.

= Fate-sharing
{parent=Internet architecture}

<Fate-sharing> places state needed by a communicating <endpoint> with that <endpoint>, so that failure of an unrelated forwarding component need not erase the state of an ongoing exchange. This can help communication recover after a route change when a path becomes available again. It does not mean every <router> lacks state or that communication can survive loss of all paths.<The design philosophy of the DARPA Internet protocols by David D. Clark>[§4: survivability and placement of essential connection state]{ref}

= IP hourglass
{parent=Internet architecture}
{c}

The <IP hourglass> describes a common narrow inter-network layer supporting many applications above it and many network technologies below it. Keeping that interface general limits the need for every application developer and link provider to coordinate separate application-specific changes.<Architectural Principles of the Internet (RFC 1958)>[§§2.1–2.4: common internetwork protocol and independence from underlying media]{ref}

= Network decentralisation
{parent=Internet architecture}

= Network decentralization
{synonym}

<Network decentralisation> concerns the distribution of relevant control, authority or indispensable dependencies across independently operated participants. It is a property relative to a specified decision or service: distributed forwarding can coexist with centralised naming, credentials or application data. Counting physical <servers> is insufficient.

= Geographical replication does not imply decentralised control
{parent=Network decentralisation}

Construct a service with replicas in ten locations, all controlled by the same operator and all requiring that operator's account authority. The physical deployment is distributed, but control and the account dependency remain centralised. Increasing the number of sites leaves that counterexample intact. To assess decentralisation, state which operators can independently authorise participation, change <protocol> behaviour or preserve service when another operator fails.

= End-to-end principle
{parent=Internet architecture}

When fully implementing a required function needs <endpoint> information, a lower-layer implementation cannot replace <endpoint> responsibility. Lower-layer mechanisms can still improve efficiency. The principle concerns function placement, not a requirement for peer-to-peer topology. <Jerome H. Saltzer>, <David P. Reed> and <David D. Clark> articulated the argument.<End-to-end arguments in system design by Jerome H. Saltzer and others>[Author-hosted reprint, pp. 1–3: the argument and careful file transfer]{ref}

= Application correctness is not determined by a network trace
{parent=End-to-end principle}

Suppose an application's required property depends on <endpoint> state that is not determined by the network trace. Consider two executions with identical messages and forwarding behaviour: in one the receiver stores the received byte correctly; in the other it corrupts that byte after reception. The network trace is the same, but the required stored-file correctness differs. Any decision based only on that trace must give the same answer in both executions and therefore cannot establish the property for all executions.

This is an indistinguishability argument for that failure model, not a claim that network checks are useless. A link checksum may reduce transmission errors while an application <endpoint> still has to check the property that spans its storage and processing. Specify the <endpoint> boundary before claiming an end-to-end guarantee.

= Communication protocol
{parent=Computer network}

= Protocol
{synonym}

A <communication protocol> specifies the format and meaning of exchanged messages and the permitted behaviour of participants. Compatibility requires agreement about both message syntax and the state changes that messages cause.

= Application-layer acknowledgement
{parent=Communication protocol}

= Application-layer acknowledgment
{synonym}

An <application-layer acknowledgement> confirms a condition specified by an application's <communication protocol>. Receipt, successful processing and durable storage are different conditions. A <Transmission Control Protocol> acknowledgement of received bytes does not itself establish any stronger application promise; the relevant <endpoint> must establish that promise.<End-to-end arguments in system design by Jerome H. Saltzer and others>[Printed p. 7: the SWALLOW example distinguishes message delivery from safe storage]{ref}

= Communication endpoint
{parent=Communication protocol}

= Endpoint
{synonym}

A <communication endpoint> is a participant at the boundary of a specified communication function. Always identify the level: a <TLS> peer, a transport <endpoint> and an application <endpoint> need not represent the same boundary of correctness or trust.

= Protocol ossification
{parent=Communication protocol}

<Protocol ossification> occurs when deployed implementations or intermediaries make established behaviour difficult to change, for example by rejecting an unfamiliar transport format or assuming fields will never evolve. <Endpoint> support alone may then be insufficient for deployment over real paths.<Report from the IAB Workshop on Stack Evolution in a Middlebox Internet (RFC 7663)>[§§2–5: interface and middlebox constraints on evolution]{ref}
