= Algorithm
{wiki}

An algorithm is a finite, precise procedure for transforming an <input> into an <output>.

Here "finite" refers to the description: a short <algorithm> can perform arbitrarily many steps on increasingly large <inputs>. Solving a <computational problem> additionally requires termination and the specified <output> on every permitted <input>. State assumptions explicitly: <binary search> requires a <sorted array>.

An <algorithm> is an idea that can have implementations in different <programming languages>. Its explanation should make three things visible: the permitted <inputs>, the rule for each step, and the meaning of the returned <output>. <Algorithm correctness> then separates finding the right answer from eventually finishing; <time complexity> asks how much work finishing requires.

A particularly useful design question is: what knowledge survives each step? In <binary search>, it is the location of every possible match inside the remaining candidate range. Writing that fact as a <loop invariant> turns an intuitive shortcut into a procedure whose discarded candidates can be justified. This often helps discover the <algorithm>, rather than merely check it afterward.

= Backward search
{parent=String-searching algorithm}

<Backward search> finds a query's matching interval in a <suffix array> by processing the query from right to left. With inclusive one-based interval $[l,r]$, prepending $c$ changes it to $[C(c)+\operatorname{Occ}(c,l-1)+1,C(c)+\operatorname{Occ}(c,r)]$. An empty interval means no match. This works through the occurrence-order property of the <last-to-first mapping>.<Opportunistic Data Structures with Applications by Paolo Ferragina and others>[§3.1, Figure 1, BW Search]{ref}

= Last-to-first mapping
{parent=String-searching algorithm}
{title2=$\operatorname{LF}(r)=C(L_r)+\operatorname{Occ}(L_r,r)$}

In a sorted <cyclic rotation> matrix, the <last-to-first mapping> sends the $k$th occurrence of a character in the last column to its $k$th occurrence in the first column. For one-based rows, $\operatorname{LF}(r)=C(L_r)+\operatorname{Occ}(L_r,r)$, where $C(c)$ counts smaller characters and $\operatorname{Occ}(c,r)$ counts $c$ in the first $r$ entries of the last column. It moves a rotation's start one character backwards cyclically. Equal characters retain the <lexicographic order> of their following sequences, which proves the occurrence-order rule.<Opportunistic Data Structures with Applications by Paolo Ferragina and others>[§2, properties (a)–(b) and LF-mapping]{ref}

= Kadane's algorithm
{parent=Maximum subarray problem}
{c}

For input $a_1,\ldots,a_n$, let $E_i$ be the largest sum of a nonempty contiguous block ending at $i$. The <recurrence relation> $E_1=a_1$ and $E_i=\max(a_i,E_{i-1}+a_i)$ is exact: an optimal block either starts at $i$ or extends an optimal block ending at $i-1$. The answer is $\max_i E_i$. Keeping only the current $E_i$ and best value gives linear <time complexity> and constant extra <space complexity>.

= Number-theoretic sieve
{parent=Algorithm}

A number-theoretic sieve processes many <integers> together by marking or updating those sharing a <divisor>, rather than testing each <integer> independently. The <sieve of Eratosthenes> marks composite multiples of successive <prime numbers>; related sieves accumulate a <smallest prime factor>, <Euler's totient function>, or <Möbius function> for every argument up to a bound. The useful structure is that the multiples of a fixed <integer> form an <arithmetic progression>, so one loop can update all affected entries in an array.

For example, initializing an array to true and then marking $2p,3p,\ldots$ for each surviving <prime number> $p$ leaves precisely the <prime numbers> unmarked, apart from the separately excluded zero and one. Every <composite number> has a <prime factor>, which proves that every composite is eventually removed. Starting the marking at $p^2$ avoids work already performed by smaller <prime numbers>. Different sieves use different update rules and <time complexity> bounds; the name alone does not imply the complexity of the <sieve of Eratosthenes>.

= Matrix-chain multiplication
{parent=Algorithm}

Given a fixed <sequence> of compatible <matrices> $A_1,\ldots,A_m$, choose a binary parenthesization of $A_1\cdots A_m$ that minimizes the number of scalar multiplications in ordinary <matrix multiplication>. The order of the <matrices> is fixed: parenthesization changes the grouping, not the operand order. <Associativity> preserves the product while intermediate <matrix> dimensions change the cost. The possible binary groupings are counted by the <Catalan number> $C_{m-1}$ for $m\geq1$.

= Matrix-chain cost model
{parent=Matrix-chain multiplication}

For <matrix dimensions> $r\times s$ and $s\times t$, ordinary <matrix multiplication> computes $rt$ <matrix entries>, each using $s$ <scalar multiplications>. Thus its cost is $rst$ <scalar multiplications>, with $rt(s-1)$ <additions> if each sum starts from its first term. Here we minimize only the <scalar multiplication> count, using this dense <matrix multiplication> rule throughout. The counts describe <arithmetic operations>, rather than measured elapsed time; <matrix multiplication> methods that exploit structure or use faster formulas require a different cost rule.

Take <matrices> $A$, $B$, $C$ with <matrix dimensions> $12\times5$, $5\times40$, $40\times3$. Both groupings produce a $12\times3$ <matrix product>, but their intermediate <matrix dimensions> differ:
$$
\begin{aligned}
(AB)C &: \quad 12\cdot5\cdot40+12\cdot40\cdot3=2400+1440=3840,\\
A(BC) &: \quad 5\cdot40\cdot3+12\cdot5\cdot3=600+180=780.
\end{aligned}
$$
The second grouping first compresses $BC$ into a $5\times3$ <matrix>, avoiding the $12\times40$ intermediate <matrix> $AB$. The saving is $3060$ <scalar multiplications>, although both groupings use exactly two <matrix multiplications>. This is why counting only <matrix multiplication> operations hides the interesting choice.

<Associativity> permits these regroupings in exact arithmetic; <commutativity> is neither assumed nor generally true for <matrix multiplication>. Swapping $A$ and $B$ here would even make their <matrix product> undefined. In <floating-point arithmetic>, <round-off error> can make the two groupings yield different computed <matrix entries>; the cost optimum alone does not guarantee the smallest numerical error.

= Matrix-chain dynamic programming
{parent=Matrix-chain multiplication}
{title2=$m[i,j]$}

Let $A_i$ have <matrix dimensions> $p_{i-1}\times p_i$, where $p_0,\ldots,p_n$ are positive <integers>. For $1\leq i\leq j\leq n$, define $m[i,j]$ as the minimum <scalar multiplication> cost of the contiguous <matrix product> $A_i\cdots A_j$. The endpoints $(i,j)$ of an <integer interval> identify a <dynamic programming state>. A single <matrix> needs no <matrix multiplication>, giving the <base case> $m[i,i]=0$. At the final <matrix multiplication>, split after $A_k$:
$$
m[i,j]=\min_{i\leq k<j}\bigl(m[i,k]+m[k+1,j]+p_{i-1}p_kp_j\bigr),\qquad i<j.
$$
The two subproducts have <matrix dimensions> $p_{i-1}\times p_k$ and $p_k\times p_j$, regardless of their internal grouping. The <recurrence relation> adds their optimal costs and the final <scalar multiplication> cost.<6.006 Introduction to Algorithms, Fall 2011 by Massachusetts Institute of Technology, 6.006 course staff/Lecture 21: Dynamic Programming III>[6.006 Introduction to Algorithms, Fall 2011 by Massachusetts Institute of Technology, 6.006 course staff; Lecture 21: Dynamic Programming III, printed p. 2, Parenthesization: final split, recurrence and zero one-matrix base case; notes use half-open indices]{ref}

Why is this <optimal substructure>? For a chosen final split $k$, replacing either subproduct's grouping by a cheaper one leaves its <matrix dimensions> and exact <matrix product> unchanged, so it decreases the whole cost by the same amount. Therefore an optimal grouping can use optimal groupings on both sides. Conversely, each candidate in the <recurrence relation> joins two achievable groupings. <Mathematical induction> on $j-i+1$, starting with the single-<matrix> <base case>, proves that the minimum is achievable and no grouping is cheaper.

There are also <overlapping subproblems>: while evaluating the different final splits of $ABCD$, the cases $A(BCD)$ and $(ABC)D$ both request the cost of $BC$. <Recursion> without reuse recomputes this answer; <memoization> or a <dynamic programming> table stores it once. Fill the table by increasing length $j-i+1$, so both dependencies are ready. Record an attaining split $s[i,j]$ alongside each cost.<6.006 Introduction to Algorithms, Fall 2011 by Massachusetts Institute of Technology, 6.006 course staff/Lecture 21: Dynamic Programming III>[6.006 Introduction to Algorithms, Fall 2011 by Massachusetts Institute of Technology, 6.006 course staff; Lecture 21: Dynamic Programming III, printed p. 2, Parenthesization: increasing substring size, cubic time and parent pointers]{ref}

The <dynamic programming> table has $n(n+1)/2$ cost entries. For length $\ell$, there are $n-\ell+1$ entries and $\ell-1$ possible splits, so the exact number of candidate evaluations is
$$
\sum_{\ell=2}^{n}(n-\ell+1)(\ell-1)=\frac{n(n-1)(n+1)}{6}.
$$
Under the unit-cost assumption that <arithmetic operations>, comparisons and access to stored costs each take constant time, this gives <time complexity> $O(n^3)$ and <space complexity> $O(n^2)$, using <Big O notation>. These bounds concern choosing a grouping from the <matrix dimensions>; they exclude the subsequent <matrix multiplication> work. If the dimensions or costs require arbitrarily long <integers>, their arithmetic and storage costs must also be counted.

= Matrix-chain split reconstruction
{parent=Matrix-chain multiplication}
{title2=$s[i,j]$}

Extend the original example by a <matrix> $D$ with <matrix dimensions> $3\times15$, so $(p_0,p_1,p_2,p_3,p_4)=(12,5,40,3,15)$. The <Catalan number> $C_3=5$ counts all possible groupings. Their <scalar multiplication> costs are
$$
\begin{array}{c|r}
\text{grouping}&\text{cost}\\\hline
((AB)C)D&2400+1440+540=4380\\
(A(BC))D&600+180+540=1320\\
(AB)(CD)&2400+1800+7200=11400\\
A((BC)D)&600+225+900=1725\\
A(B(CD))&1800+3000+900=5700
\end{array}
$$
The optimum is $(A(BC))D$, with cost $1320$. Enumeration makes a useful check here, but <dynamic programming> reaches the same answer by solving ten <integer intervals>, including the four single-<matrix> <base cases>:
$$
\begin{array}{c|rrrr}
i\backslash j&1&2&3&4\\\hline
1&0&2400&780&1320\\
2&&0&600&825\\
3&&&0&1800\\
4&&&&0
\end{array}
$$
For example, $m[2,4]=\min\{1800+5\cdot40\cdot15,\ 600+5\cdot3\cdot15\}=\min\{4800,825\}=825$. The three final-split candidates for the full <matrix product> supply a compact certificate:
$$
\begin{aligned}
k=1 &: \quad 0+825+12\cdot5\cdot15=1725,\\
k=2 &: \quad 2400+1800+12\cdot40\cdot15=11400,\\
k=3 &: \quad 780+0+12\cdot3\cdot15=1320.
\end{aligned}
$$
The first candidate already uses the better grouping of $BCD$; the worse $A(B(CD))$ need not be reconsidered at the top level. This is how <optimal substructure> lets the table represent all five possibilities with only three final candidates.

Read $s[1,4]=3$, which separates $ABC$ from $D$. Then $s[1,3]=1$ separates $A$ from $BC$, and $s[2,3]=2$ separates $B$ from $C$. This <recursion> stops at every $i=j$, returning the corresponding <matrix> name. Combining the returned expressions recovers $(A(BC))D$, rather than only its cost. Every <recursive call> uses a shorter <integer interval>, establishing <algorithm termination>; a tied minimum may choose any attaining split. The recovered <binary tree> has $n$ leaves and $n-1$ internal nodes, so reconstruction takes $O(n)$ steps. Its attraction is the separation between an enormous family of groupings and a small set of reusable <dynamic programming states>.

= Greedy algorithm
{parent=Algorithm}
{wiki}

= Greedy
{synonym}

A <greedy algorithm> builds a <feasible solution> by repeatedly committing to a locally preferred next choice. Each commitment is final: the <algorithm> does not revisit it when later choices become available. In <mathematical optimization>, the important question is whether those commitments can still attain the best <objective function> value.

For example, a shared telescope can accept several observation requests with fixed time slots. In <interval scheduling>, every completed request counts equally, and overlapping requests cannot both be accepted. Choosing the request that finishes earliest leaves the resource available sooner. The example below turns that intuition into a precise rule, then shows why choosing the earliest start or shortest duration can lose jobs.

<Greedy algorithms> are attractive because a single pass can replace a search through many candidate <subsets>. However, "locally best" is only a design proposal. A problem-specific <greedy-choice property>, often established by an <exchange argument>, must connect the local decision to the actual <objective function>. The largest-individual-value rule in the <0-1 knapsack problem> fails; <Dijkstra's algorithm> needs its nonnegative-edge assumptions. A rule's success in one <optimization> task does not justify it in another.

= Greedy-choice property
{parent=Greedy algorithm}

A <greedy-choice property> says that some optimal <feasible solution> contains the locally selected choice. Together with <optimal substructure> in the remaining instance, it allows repeated commitments. An <exchange argument> often establishes this property.<Algorithms by Jeff Erickson/Greedy Algorithms>[Algorithms by Jeff Erickson; §4.3 General Pattern, printed pp. 164–165: exchange without worsening an optimum]{ref}

For <interval scheduling>, a safe first choice need not belong to every optimal <feasible solution>. When several optima exist, a commitment may exclude one while retaining another. The useful <loop invariant> is that the accepted prefix can still be extended to an optimum. Merely keeping the accepted <intervals> compatible proves feasibility, which is a weaker claim.

= Exchange argument
{parent=Greedy-choice property}

An <exchange argument> modifies an optimal <feasible solution> to include a desired choice while preserving feasibility and not worsening its <objective function> value. The modification need not strictly improve the optimum; equality suffices.<Algorithms by Jeff Erickson/Greedy Algorithms>[Algorithms by Jeff Erickson; §4.3 General Pattern, printed pp. 164–165: exchange at the first disagreement]{ref}

For <interval scheduling>, the exchange replaces the first selected job with an earliest-finishing job. Its safety comes from the finish-time inequality below. Replacing a job with a shorter one has no such guarantee: it might move the occupied <interval> into the middle of two useful jobs, as the <shortest-duration interval scheduling counterexample> shows.

= Interval scheduling
{parent=Greedy algorithm}
{wiki}
{title2=$\max |S|$}

Given a <finite set> of jobs with fixed half-open <intervals> $[s_i,f_i)$, where $s_i<f_i$, choose a <subset> $S$ of <maximum> <cardinality>. Each job occupies one shared resource throughout its <interval>. A <feasible solution> has pairwise <disjoint> <intervals>: for distinct selected jobs $i,j$, either $f_i\leq s_j$ or $f_j\leq s_i$. Thus a finish and the next start may coincide. Every job has value one; occupied time is not the <objective function>.<6.046J Design and Analysis of Algorithms, Spring 2015/Lecture 1: Introduction>[6.046J Design and Analysis of Algorithms, Spring 2015; Printed p. 2, Interval Scheduling: fixed requests, one resource, compatibility with endpoint equality, maximum size]{ref}

Consider these six original jobs, with arbitrary time units:
$$
\begin{array}{c|rrrrrr}
\text{job}&A&B&C&D&E&F\\\hline
s_i&0&1&3&5&6&8\\
f_i&6&3&5&7&9&10
\end{array}.
$$
Job $B=[1,3)$ can be followed immediately by $C=[3,5)$ and $D=[5,7)$. Job $A=[0,6)$ conflicts with all three. Starting the resource earlier is therefore not automatically beneficial: one long commitment can displace several shorter requests.

The earliest-finish <greedy algorithm> uses a <sorting algorithm> to put jobs in <nondecreasing> finish time. Scan that order, accepting the first job and then each job whose start is at least the last accepted finish. Break finish-time ties arbitrarily; an empty <input> returns the <empty set>. For these jobs, the order and decisions are
$$
\begin{array}{c|rrrrrr}
\text{finish order}&B&C&A&D&E&F\\\hline
\text{decision}&\text{take}&\text{take}&\text{skip}&\text{take}&\text{skip}&\text{take}
\end{array}.
$$
After $B,C$, job $A$ starts before the current finish five and is rejected. Accept $D$; then reject $E=[6,9)$ because six is before seven. Finally accept $F=[8,10)$. The result is $S=\{B,C,D,F\}$, with <cardinality> four. Leaving $[0,1)$ idle makes room for more jobs.

By contrast, the earliest-start rule scans $A,B,C,D,E,F$. It accepts $A$, skips $B,C,D$, accepts $E$, and skips $F$. Its <feasible solution> $\{A,E\}$ contains only two jobs. Here $A$ and $E$ meet at time six and are compatible; $E$ and $F$ overlap on $[8,9)$.

There is also an elementary optimality certificate for this example. The four <subsets> $\{A,B\}$, $\{C\}$, $\{D,E\}$ and $\{F\}$ form a <partition of a set> of the jobs. A <feasible solution> takes at most one job from each group: $A,B$ overlap, as do $D,E$, and each other group is a <singleton>. Hence four is an <upper bound>, attained by $\{B,C,D,F\}$. Checking all $2^6=64$ <subsets> gives a unique optimum of size four: $\{B,C,D,F\}$.

The earliest-finish theorem states that this <greedy algorithm> maximizes job count for every finite instance of <interval scheduling>. For the <exchange argument>, let $q$ be the first job in an optimal <feasible solution> and $g$ an earliest-finishing job. Every later selected job $j$ satisfies
$$
f_g\leq f_q\leq s_j.
$$
Replace $q$ by $g$; compatibility and <cardinality> survive. The remainder must be optimal among jobs starting at or after $f_g$, or improving it would improve the whole selection. <Mathematical induction> on the smaller remaining instance, starting with the <empty set>, completes the outline.<Algorithms by Jeff Erickson/Greedy Algorithms>[Algorithms by Jeff Erickson; §4.2 Scheduling Classes, Lemma 4.3 and Theorem 4.4, printed pp. 163–164; endpoint equality is allowed by our half-open convention]{ref}

Why is the <algorithm> fast? Once sorted, each job is examined once, using only the last accepted finish to decide compatibility. The scan takes $O(n)$ time; comparison <sorting algorithms> give total <time complexity> $O(n\log n)$ for $n\geq2$, in <Big O notation>, assuming constant-cost endpoint comparisons. Already sorted <input> needs only the $O(n)$ scan.<6.046J Design and Analysis of Algorithms, Spring 2015/Lecture 1: Introduction>[6.046J Design and Analysis of Algorithms, Spring 2015; Printed pp. 2–4, earliest-finish rule, compatibility and first-job exchange; scan cost follows by counting one comparison per subsequent request]{ref}

The reason the shortcut is correct is stronger than "finishing sooner looks good": the <exchange argument> preserves every later job of a suitable optimum. This is the problem-specific fact that permits final decisions without exploring all <subsets>.

= Shortest-duration interval scheduling counterexample

In this separate three-job example, labels $A,B,C$ denote new jobs:
$$
A=[0,5),\qquad B=[5,10),\qquad C=[4,6).
$$
Their durations are five, five and two. Consider the rule "accept a shortest remaining job, discard all jobs conflicting with it, and repeat". It selects $C$ first. But $C$ overlaps $A$ on $[4,5)$ and $B$ on $[5,6)$, so both are discarded. The rule returns one job, while the compatible <subset> $\{A,B\}$ contains two. The common endpoint five is allowed, and no <feasible solution> contains all three jobs, so two is the <maximum>.

= Weighted interval scheduling
{parent=Interval scheduling}
{title2=$\max\sum_{i\in S}w_i$}

<Weighted interval scheduling> assigns each job a reward $w_i$ and maximizes their sum over compatible jobs. Earliest finish can fail for this different <objective function>; <dynamic programming> can compare alternatives.<6.046J Design and Analysis of Algorithms, Spring 2015/Lecture 1: Introduction>[6.046J Design and Analysis of Algorithms, Spring 2015; Printed pp. 4–5, Weighted Interval Scheduling and Dynamic Programming]{ref}

For a separate two-job example, let $X=[0,2)$ have reward one and $Y=[1,3)$ reward ten. Earliest finish accepts $X$ and rejects $Y$, earning one; the optimum accepts $Y$, earning ten. = Algorithm correctness
{parent=Algorithm}

<Partial correctness> means that, if the <algorithm> terminates on a permitted <input>, its <output> meets the <formal specification>. <Total correctness> additionally requires <algorithm termination> on every permitted <input>.

A <precondition> $P$ describes permitted starting circumstances; a <postcondition> $Q$ describes the required result. <Partial correctness> says that starting with $P$ and finishing implies $Q$. <Total correctness> also guarantees finishing. A <loop invariant> supplies the connection between these conditions during repeated steps.<CS 2112 Fall 2019/Loop invariants>[CS 2112 Fall 2019; Loop invariants, Using loop invariants to show code is correct: Establishment, Preservation, Postcondition, and Termination]{ref}

Correctness is relative to a <formal specification>. Returning the first entry of an <array> correctly implements "return the first entry", but fails "return the <maximum>" on $[3,1,4,4,2]$. A fast wrong answer does not acquire <algorithm correctness> from its <time complexity>. Numerical closeness matters only when the <formal specification> allows an approximation. <Software testing> and <test coverage> provide evidence about selected executions; they do not by themselves establish <algorithm correctness> for every permitted <input>.

= Partial correctness
{parent=Algorithm correctness}

<Partial correctness> means that every terminating execution begun in a <program state> satisfying the <precondition> $P$ finishes in a <program state> satisfying the <postcondition> $Q$. For a sequential program $C$, the usual <Hoare triple> notation is
$$
\{P\}\ C\ \{Q\}.
$$
Here the notation expresses <partial correctness>; it makes no promise that $C$ finishes. The <precondition> and <postcondition> describe permitted starting circumstances and required final circumstances, rather than tests performed automatically by the program.<An Axiomatic Basis for Computer Programming by Tony Hoare>[Hoare, 1969, §3 Program Execution, p. 577, and §4 General Reservations, pp. 578–579; the paper instead labels the precondition P, program Q and result R]{ref}

For a sharp example, take the <precondition> $n=4$ and the following sequential program over mathematical <integers>:
``
i = 0
s = 0
while i < n:
    i = i
``
The condition remains true, so execution never reaches the instruction after the loop. Consequently its <partial correctness> claim holds for the <postcondition> $2s=n(n+1)$, and even for the impossible <postcondition> $0=1$: there is no terminating execution with a wrong final result. This is <vacuous truth>, not evidence that the loop computes a <sum>. The same program fails <total correctness> for this permitted <input>.

The distinction is useful in a proof: first show that an answer, whenever produced, is right; then establish <algorithm termination>. The <summation loop verification> supplies both arguments for a loop that actually progresses. Its finite trace illustrates one execution, while its <loop invariant> covers every permitted <input>.

= Total correctness
{parent=Algorithm correctness}

<Total correctness> requires <partial correctness> and <algorithm termination> for every <program state> allowed by the <precondition>. For a deterministic sequential program, every permitted start must reach a final <program state> satisfying the <postcondition> after finitely many steps. Thus an infinite execution can satisfy <partial correctness>, but refutes <total correctness> for a permitted start.

In the <summation loop verification>, the <loop invariant> establishes the answer conditional on exit, and the <loop variant> establishes exit. Both parts matter: replacing the body by a step that never returns would defeat <total correctness> even if every completed iteration preserved the <loop invariant>. Likewise, a terminating loop with the wrong <sum> fails <partial correctness> and therefore fails <total correctness>.

These obligations depend on the <formal specification>. A program that rejects every <input> might correctly implement a rejection service, but does not meet a contract promising a <sum> for every nonnegative <integer>. A proof of <total correctness> also gives no particular physical response-time guarantee: <time complexity> and the execution environment require their own assumptions.

= Algorithm termination
{parent=Total correctness}

<Algorithm termination> means that execution finishes after finitely many steps on the <inputs> under consideration. Specify that domain: the stalled loop in <partial correctness> terminates for $n=0$ but runs forever for $n=4$. A successful run on one <input> does not establish termination on another.

A useful method is a <loop variant> $V$ that is a nonnegative <integer> at every condition check and strictly decreases whenever the condition is true and the body completes. Also prove that condition evaluation and each body execution terminate. An infinite run would then give an infinite strictly decreasing <sequence> of nonnegative <integers>, contradicting their <well-founded relation>. This establishes <algorithm termination> without enumerating all executions.

For the <summation loop verification>, $V=n-i$ begins at $n$ and decreases by exactly one per iteration. The body executes exactly $n$ times, including zero times for $n=0$. Merely bounding a decreasing measure below is insufficient for <real numbers>: $1,1/2,1/4,\ldots$ decreases forever while staying positive. The choice of a <well-founded relation> supplies the essential progress argument; <well-founded progress in recursion> applies the same idea to <recursive calls>.

= Prefix maximum correctness example
{parent=Algorithm correctness}

Given a nonempty finite <sequence> $a=(a_0,\ldots,a_{n-1})$ of <integers>, return its <maximum> value. Represent the <sequence> by an <array> whose contents remain unchanged during execution. The <precondition> requires an <integer> length $n\geq1$ and exact, terminating <integer> comparisons and <variable assignments>. The <postcondition> for returned value $r$ is
$$
r\in\{a_i:0\leq i<n\}\quad\text{and}\quad a_i\leq r\ \text{for every }0\leq i<n.
$$
Thus the <output> belongs to the <finite set> of entries and is at least every entry. The contract permits ties and negative <integers>; it asks for a value, not the position of a particular occurrence. There is no <maximum> of an empty <set> of <integers>, so empty <input> is deliberately outside this <precondition>. A service accepting empty <inputs> needs a different <formal specification>, such as a separate absent result.

This <Python> implementation makes the <variable assignments> explicit. Its index arithmetic models exact <integer> arithmetic; fixed-width implementations additionally need enough index range for $n$:
``
def find_max(a):
    n = len(a)
    best = a[0]
    k = 1
    while k < n:
        if a[k] > best:
            best = a[k]
        k = k + 1
    return best
``
For the original <input> $[3,1,4,4,2]$, initialization gives $k=1$ and $\mathrm{best}=3$. Reading $a_1=1$ keeps $3$; reading $a_2=4$ changes it to $4$; reading $a_3=4$ and $a_4=2$ keeps $4$. At successive condition checks, the pairs $(k,\mathrm{best})$ are $(1,3),(2,3),(3,4),(4,4),(5,4)$. The returned <maximum> is $4$.

\Image[prefix-maximum-invariant-trace.png]
{title=<Maximum> values of successive prefixes in the original <integer> <array>}
{description=Each row shows the processed prefix of $[3,1,4,4,2]$ immediately before checking $k<n$. Blue cells have been processed; grey cells have not. The <loop invariant> records the <maximum> of the blue entries, while the <loop variant> $n-k$ counts remaining entries. These are exact constructed execution states.}

At each condition check, use the <loop invariant>
$$
I:\qquad 1\leq k\leq n,\qquad \mathrm{best}=\max\{a_i:0\leq i<k\},
$$
together with the fact that the <input> <array> is unchanged. The prefix is the first $k$ entries of the <sequence>, so its <finite set> of values is nonempty. The <maximum> need not be unique as an occurrence: the invariant concerns its value.

Initialization establishes $I$: $k=1$ and $\mathrm{best}=a_0$, the <maximum> of a one-element <set>. For preservation, suppose $I$ and $k<n$ hold. Then $a_k$ is a valid <array> entry. Either the comparison replaces $\mathrm{best}$ with the larger value $a_k$, or it keeps a value at least $a_k$. Before increasing $k$, the resulting value is
$$
\max\bigl(\max\{a_i:0\leq i<k\},a_k\bigr)=\max\{a_i:0\leq i<k+1\}.
$$
The <variable assignment> $k\gets k+1$ restores the complete <loop invariant>. Between the two <variable assignments>, the old prefix formula may temporarily be false; the <loop invariant> is required at condition checks, not at every instruction.

At exit, $k\geq n$, while $I$ gives $k\leq n$. Hence $k=n$, and $I$ gives exactly the required <postcondition>. This establishes <partial correctness>. The preservation argument is <mathematical induction> on the number of completed iterations, covering every permitted <integer> <sequence>, rather than just the pictured <input>.

For <algorithm termination>, the <loop variant> $V=n-k$ is a nonnegative <integer> whenever $I$ holds. If $k<n$, then $V\geq1$. Every body terminates under the <precondition> and changes $V$ to $V-1$. Starting at $n-1$, it reaches zero after exactly $n-1$ iterations. For $n=1$, the initial value is already zero and the body is never entered. Together with <partial correctness>, this proves <total correctness>.

Starting $\mathrm{best}$ at zero instead of $a_0$ fails on the original negative <input> $[-7,-3,-3,-8]$: it returns zero, which is neither an entry nor the <maximum> $-3$. Keeping $k=1$ forever preserves the correct initial prefix claim but loops forever when $n>1$; a <loop invariant> alone does not ensure <algorithm termination>. Using `>=` instead of `>` still returns the same <maximum> value when entries tie, although a version returning a position would need an explicit tie rule.

= Formal verification
{parent=Algorithm correctness}

Establishing specified properties of a system using <formal proofs> about a precise model. <Formal verification> connects an implementation to a <formal specification>; correctness of the model and its assumptions still matters when applying the result to a physical system.

For a small example, the <summation loop verification> below starts with executable steps and asks two separate questions: does any returned value satisfy the <postcondition>, and does execution reach that return? A <loop invariant> answers the first; a <loop variant> answers the second. This turns an unbounded family of permitted <inputs> into a few reusable proof obligations.

The model must specify <programming language semantics>, including the meaning of <variable assignments>, comparisons and <integer arithmetic>. A proof about exact mathematical <integers> need not describe a machine that wraps on <integer overflow>. Similarly, a correct <formal proof> of a weak or mistaken <formal specification> does not establish the intended behavior. Choosing the right <formal specification> and relating the model to the implemented system remain substantive tasks.

<Software testing> examines chosen executions and can expose a <counterexample>. A <formal proof> instead justifies a statement throughout its stated model; it does not require executing every permitted <input>. This makes <formal verification> valuable when rare boundary cases matter, while <software testing> can still reveal an incorrect model or misunderstood requirement.

In 1969, <Tony Hoare> presented rules for <variable assignment>, composition and iteration in a small <programming language>. His paper explicitly says those rules do not prove successful termination, and discusses the dependence of arithmetic reasoning on the chosen overflow behavior. These reservations already make the model's scope part of the argument.<An Axiomatic Basis for Computer Programming by Tony Hoare>[Hoare, An Axiomatic Basis for Computer Programming, §2 Computer Arithmetic, pp. 576–577; §§3.1–3.4, pp. 577–578; §4 General Reservations, pp. 578–579]{ref}

= Summation loop verification
{parent=Formal verification}
{title2=$2s=n(n+1)$}

Compute $1+2+\cdots+n$, the <triangular number> $T_n$, for a nonnegative <integer> $n$. The <empty sum> gives zero when $n=0$. Use exact mathematical <integers> and keep the <input> $n$ unchanged; every comparison and <variable assignment> is a terminating operation. The original sequential procedure is
``
require n is an integer and n >= 0
i = 0
s = 0
while i < n:
    i = i + 1
    s = s + i
return s
``
The order of the two <variable assignments> matters: the <addition> uses the newly incremented $i$. For $n=4$, the pairs $(i,s)$ at successive condition checks are $(0,0),(1,1),(2,3),(3,6),(4,10)$. At the last check, $i<n$ is false, and the returned <sum> is $10$.

The <precondition> is $n\in\mathbb Z$ with $n\geq0$, under the exact-arithmetic model just stated. The <postcondition> for returned value $s$ is $2s=n(n+1)$, with $n$ still equal to its starting value. At each condition check use the <loop invariant>
$$
I:\qquad i,s\in\mathbb Z,\qquad 0\leq i\leq n,\qquad 2s=i(i+1),
$$
and the <loop variant> $V=n-i$. The equation says that the accumulator is the <triangular number> for precisely the processed prefix $1,\ldots,i$; the inequalities connect that prefix to the loop's condition.

\Image[summation-loop-contract-control-flow.png]
{title=The summation loop restores its invariant before each condition check}
{description=Original sequential control flow for the <summation loop verification>. The blue loop head carries the <loop invariant>; the orange body increments $i$ before adding it to $s$. A false condition leads to the <postcondition>. The <loop variant> decreases on the return arrow. All values are mathematical <integers> and $n$ remains unchanged.}

Initialization gives $i=s=0$, so $I$ holds, including when $n=0$. For preservation, let the old values satisfy $I$ and $i<n$. Write $i'=i+1$ and $s'=s+i'$ for the values after both <variable assignments>. Since $i,n$ are <integers>, $i<n$ gives $i'\leq n$, and
$$
2s'=2s+2(i+1)=i(i+1)+2(i+1)=(i+1)(i+2)=i'(i'+1).
$$
Thus the completed body restores $I$. Between the two <variable assignments>, the equation can be false; the <loop invariant> is required at the loop head. This preservation step is <mathematical induction> on the number of completed iterations.

At exit, the false condition gives $i\geq n$, while $I$ gives $i\leq n$. Hence $i=n$, so $2s=n(n+1)$: this proves <partial correctness>. For <algorithm termination>, $I$ gives the nonnegative <integer> $V=n-i$. When the condition is true, $V\geq1$; the terminating body gives $V'=n-i'=V-1$. Therefore the loop cannot repeat forever. Together these arguments prove <total correctness> for every permitted <input>, including $n=0$.

\Image[summation-loop-trace-and-stalled-variant.png]
{title=Four additions finish the sum; an unchanged index cannot make progress}
{description=Original exact trace for $n=4$: five condition checks and four body executions give $s=10$, while the <loop variant> decreases from four to zero. The right panel shows the stalled loop from <partial correctness>: the same <program state> repeats and $V=4$ never decreases. Its equation $2s=i(i+1)$ remains true, but it never reaches an exit.}

Two changes expose what the proof checks. Swapping the two body instructions computes $0+1+\cdots+(n-1)$, returning $6$ rather than $10$ for $n=4$. Leaving $i$ unchanged can preserve an initial equation forever without producing any answer. The first change breaks the intended <postcondition>; the second breaks <algorithm termination>. A trace can reveal these failures, while the two proof obligations explain them.

The exact-arithmetic assumption has a concrete boundary. In a stipulated unsigned eight-<bit> model where each <addition> wraps modulo $256$, $n=23$ fits in the <input> representation, but its intended <triangular number> is $276$. The stored accumulator instead finishes at $20$, so the mathematical <postcondition> fails. This is <integer overflow>, and the proof above does not apply to that altered model. Restricting the same implementation to $0\leq n\leq22$ prevents overflow in its stored loop values, since $T_{22}=253$; alternatively use a representation supporting the required exact <integer arithmetic>. The equations in the proof are mathematical statements, not instructions to evaluate products in eight <bits>.

= Formal specification
{parent=Formal verification}

A mathematically precise description of permitted behaviour. A <formal specification> for the <microkernel file-read example>'s service could relate an authorized request to the exact returned <bytes>; a <formal specification> of its <microkernel>'s <IPC> need only describe the protected transport operation. They state different obligations.

For the <summation loop verification>, require a nonnegative <integer> <input> $n$ and a returned value $s$ satisfying $2s=n(n+1)$. The <formal specification> describes what answer is acceptable without requiring this particular loop: another implementation may satisfy the same contract. State separately whether <partial correctness> or <total correctness> is required. A <Hoare triple> packages the <precondition>, the program and the <postcondition>; <Hoare logic> supplies rules for establishing such claims.

Precision alone does not ensure a useful requirement. The <postcondition> $s\geq0$ permits returning zero for every nonnegative <integer> <input>; it does not specify the intended <triangular number>. Conversely, an impossible <precondition> permits no starts, making a universal correctness claim vacuous. Check both that intended <inputs> are admitted and that admitted <outputs> express the intended task.

= Precondition
{parent=Formal specification}

The condition required of a starting <program state> for a stated correctness guarantee. In the <summation loop verification>, $n\in\mathbb Z$ and $n\geq0$ admit $n=0$ and $n=4$, but exclude $n=-1$. The accompanying model assumes exact <integer arithmetic> and terminating elementary operations. The initial values of $i,s$ need no restriction because initialization overwrites them before use.

A <precondition> is a logical assumption, not automatically an executable check. Writing `require` in a procedure states its contract; an implementation that checks or rejects invalid <inputs> needs that behavior specified too. Weakening a <precondition> admits more starts and therefore demands more proof: dropping $n\geq0$ here makes $n=-2$ a terminating <counterexample> to $2s=n(n+1)$, since initialization returns zero while $n(n+1)=2$.

= Postcondition
{parent=Formal specification}

The condition required of a final <program state> when a program finishes under its <precondition>. The <summation loop verification> requires returned value $s$ to satisfy $2s=n(n+1)$ and preserves the <input> $n$. Relating the answer to the original <input> matters: allowing the program to replace $n$ by zero would change the intended contract.

A <postcondition> alone gives no promise of <algorithm termination>. It also need not specify a unique <output>: $s\geq0$ allows many answers, while the exact <triangular number> equation determines one <integer> answer for each permitted $n$. Stronger <postconditions> express more obligations; proving only a weaker consequence cannot justify the stronger requirement.

= Binary correctness
{parent=Formal verification}

Conformance of compiled machine code to the behaviour of the code model used to justify it. <Binary correctness> can extend <formal verification> across the compilation step; the result applies to the particular compiled artifact and its assumptions.

= Functional correctness
{parent=Algorithm correctness}

Conformance of an implementation's behaviour to its specified functional requirements. The exact obligations come from the <formal specification>: correct delivery of an <IPC> payload and correct computation of a <file> read are different requirements. Neither requirement by itself supplies a numerical response-time bound.

= Loop invariant
{parent=Algorithm correctness}
{wiki}

A statement true whenever execution reaches a chosen point in a loop, usually immediately before its condition is tested. Establish it initially, preserve it through each iteration, and combine it with the exit condition to establish <algorithm correctness>. Termination needs a separate argument.<CS 2112 Fall 2019/Loop invariants>[CS 2112 Fall 2019; Loop invariants, Using loop invariants to show code is correct: the three partial-correctness obligations and separate Termination step]{ref}

Write $I$ for the <loop invariant>, $B$ for the condition, $P$ for the <precondition>, and $Q$ for the <postcondition>. Prove that initialization under $P$ establishes $I$, that a completed body starting with $I$ and $B$ restores $I$, and that $I$ with false $B$ implies $Q$.<CS 2112 Fall 2019/Loop invariants>[CS 2112 Fall 2019; Loop invariants, Using loop invariants to show code is correct: Establishment, Preservation, and Postcondition]{ref}

In the <prefix maximum correctness example>, the <loop invariant> remembers exactly the <maximum> of the processed prefix and the valid index bounds. The weaker statement $\mathrm{best}\geq a_0$ survives every iteration, but does not imply the <postcondition>: for $[3,1,4,4,2]$, the wrong value $3$ satisfies it. A useful <loop invariant> retains enough information to recover the answer when the condition becomes false.

= Loop variant
{parent=Loop invariant}
{title2=$V$}

A decreasing measure used to prove <algorithm termination>. A nonnegative <integer> <loop variant> must strictly decrease after every completed body whose condition was true; the body itself must terminate.<CS 2112 Fall 2019/Loop invariants>[CS 2112 Fall 2019; Loop invariants, Using loop invariants to show code is correct: Termination and the decrementing function]{ref}

The <prefix maximum correctness example> uses $V=n-k$. It counts unread entries and is independent of whether the new entry changes the <maximum>. Ties therefore cannot stall progress: $k$ increases even when $\mathrm{best}$ stays the same. An <integer> bounded below cannot strictly decrease indefinitely, which supplies the missing <algorithm termination> argument.

= Linear search
{parent=Algorithm}
{wiki}

= Sequential search
{synonym}

<Linear search>, also called <sequential search>, examines a finite <sequence> from its beginning, performing an <equality test> on each entry until one matches the target or the entries run out. It needs no <sorted array> or <total order> on the values. This makes it useful for a small collection, a one-off lookup, or data available only in succession: the next entry is enough to make progress.

Specify the answer precisely. For an <array> $A$ of length $n\geq0$ with indices $0,\ldots,n-1$ and target $x$, return the smallest index $j$ satisfying $A_j=x$, or a distinct absent result if no such index exists. Repeated values are allowed. In this contract, finding a later duplicate is insufficient when an earlier match exists. Assume the <input> remains unchanged during the search and each <equality test> terminates with a stable truth value expressing the intended matching relation.

Here is an implementation in <Python>; `None` represents absence and is distinct from the valid index zero:
``
def linear_search(entries, target):
    for index, entry in enumerate(entries):
        if entry == target:
            return index
    return None
``
The official <Python> <sequence> method `s.index(x)` likewise specifies the first occurrence, but signals absence by raising `ValueError`. An API's absent-result convention belongs to its contract.<Python 3.14 documentation/Built-in Types, Python 3.14 documentation>[Python 3.14 documentation, Common Sequence Operations: s.index(x), first occurrence and ValueError]{ref}

Take the original unsorted <array> $A=[7,4,7,2,9]$. For $x=7$, the first <equality test> succeeds and returns index $0$; the other $7$ at index $2$ is never inspected. For $x=2$, the checks against $7,4,7$ fail, the check against $2$ succeeds, and the answer is index $3$ after four <equality tests>. For absent target $x=6$, all five <equality tests> fail and the answer is `None`. On the empty <sequence>, there is no entry to inspect: return `None` with zero <equality tests>.

{title=<Linear search> on an unsorted <array>: first duplicate, later match, and absent target}
{description=Indices start at zero. Each numbered cell is one <equality test>; green cells match, orange cells fail, and grey cells are never inspected. The empty <sequence> requires zero <equality tests>.}

Value order never justifies skipping an entry in this <algorithm>. For $x=2$, stopping because the first value $7$ is larger would give a wrong absent result. Any <permutation> of the <input> remains searchable by <linear search>, although the first matching index and number of <equality tests> can change. By contrast, <binary search> uses a <total order> and the <sorted array> property to discard whole candidate ranges. Its logarithmic <time complexity> additionally assumes cheap access to middle entries; a sorted <linked list> does not acquire constant-cost indexed access merely by being sorted. Sorting for a single query also has a cost, and changes positions relative to the original <sequence>.

= Linear search comparison count
{parent=Linear search}
{title2=$C$}

Count just the <equality tests> between the target and an entry, excluding loop conditions and index updates. If the first match is at index $j$, <linear search> uses exactly $C=j+1$ <equality tests>. If the target is absent, it uses exactly $C=n$. Thus for $n\geq1$ the best successful case costs one <equality test>, and the worst case costs $n$, attained by absence or a first match at the last index. For $n=0$, the sole outcome is absence with $C=0$.

\Image[linear-search-position-comparison-count.png]
{title=<Linear search comparison count> depends on the first matching position}
{description=For length $n=8$, a first match at index $j$ costs $j+1$ <equality tests>; absence costs eight. The dashed mean $4.5$ assumes a successful unique target uniformly located over the eight positions. It does not include absent queries.}

An <expected value> needs a specified <probability distribution>. For $n\geq1$, condition on success, assume the target occurs exactly once, and assume its position $J$ has a <uniform distribution on a finite set> of indices $0,\ldots,n-1$. Then the <expected value> of the <linear search comparison count> is
$$
\mathbb E[C\mid\text{success}]=\frac{1}{n}\sum_{j=0}^{n-1}(j+1)=\frac{n+1}{2}.
$$
This is the average of the costs $1,2,\ldots,n$ under those assumptions, with no assumption that the <array> is sorted. It is not a universal average for arbitrary queries. For example, with $n=5$, a unique successful target at index $0$ with <probability> $3/4$ and at index $4$ with <probability> $1/4$ has <expected value> $(3/4)\cdot1+(1/4)\cdot5=2$, rather than $3$.

Duplicates also require care about what is sampled. Choose a position uniformly in $[7,4,7,2,9]$, then search for its value. All queries succeed, but the five possible sampled positions give costs $1,2,1,4,5$: both positions holding $7$ cause an immediate match at index $0$. The <expected value> is $13/5$, not $(5+1)/2$. Uniformly choosing an occurrence does not uniformly locate the first match.

More generally, let the success <probability> be $p>0$ and let $q_j$ be the conditional <probability> that the first matching index is $j$, allowing duplicates. Since $\sum_{j=0}^{n-1}q_j=1$, the <expected value> is
$$
\mathbb E[C]=p\sum_{j=0}^{n-1}(j+1)q_j+(1-p)n.
$$
Under the unique, uniformly located successful-target assumptions this becomes $p(n+1)/2+(1-p)n$. If every query is absent, $p=0$ and $C=n$ without needing conditional probabilities. When $n=0$, success is impossible and $C=0$; the successful-search conditional formula is undefined.

Converting the <linear search comparison count> to execution time needs a cost model. Under constant-cost <equality tests>, next-entry access, and loop bookkeeping, worst-case <time complexity> is $O(n)$ in <Big O notation> for $n\geq1$, with constant overhead even for the empty <sequence>. Variable-length entries can make an <equality test> expensive. On a <linked list>, advance along its links; repeatedly restarting at the head to obtain the next numeric index adds work that the comparison count does not capture. These are exact operation counts and conditional mathematical averages, not runtime measurements.

= Linear search correctness
{parent=Linear search}

The <loop invariant> just before inspecting index $i$ is: $0\leq i\leq n$, and no entry at an index $k<i$ matches $x$. Initially $i=0$, so there are no earlier entries. A failed <equality test> extends the excluded region by one position and preserves the <loop invariant>. A successful <equality test> at index $i$ establishes a match; the <loop invariant> establishes that it is the first one. At exhaustion, $i=n$ and every entry has failed, so the absent result is correct. The number $n-i$ of remaining entries decreases after each failed <equality test>, proving termination for a finite <sequence>. Together these establish <algorithm correctness> under the assumptions that the <input> is stable and each <equality test> terminates. No step of the argument compares the relative order of values.

= Equality test
{parent=Algorithm}
{title2=$a=x$}

A terminating check returning whether two values match under a specified relation. Mathematical equality is one such relation; a chosen <equivalence relation> can instead express matching keys. <Linear search> only needs this check, whereas <binary search> also uses relative order. The cost of an <equality test> depends on the representation and implementation of its operands.

= Strength reduction
{parent=Algorithm}

Replace an operation by an equivalent operation sequence with lower cost on the target machine. For fixed-width wrapping integers, multiplication by eight equals left shift by three, and multiplication by fifteen equals left shift by four minus the original operand. Condition codes and wider results must also be preserved if the original machine instruction exposes them.

= Depth-first traversal
{synonym}

<Depth-first search> is a <graph search> that follows a branch as far as it can before returning to try the next unexplored branch. Starting at a <vertex> $s$ of an <undirected graph> on a <finite set> of <vertices>, mark $s$ as discovered. Scan its <graph neighbours> in a fixed order: for each undiscovered <vertex>, record the current <vertex> as its <parent in a rooted tree> in the discovery <tree>, mark the new <vertex>, and explore it immediately using <recursion>. Return when its <adjacency list> is exhausted. Discovery marks persist after return, preventing a <graph cycle> from causing repeated exploration. This branch-and-return rule is the maze exploration described in MIT's notes. <6.006 Introduction to Algorithms, Fall 2011 by Massachusetts Institute of Technology, 6.006 course staff/Lecture 14: Graphs II: Depth-First Search>[MIT 6.006, lecture 14: depth-first search, pp. 2–3]{ref}

Use the same unweighted <undirected graph> as <breadth-first search>, with <vertex set> $V=\{A,B,C,D,E,F,G\}$ and <edges>
$$
E=\{AB,AC,BD,BE,CE,CF,EG,FG\},
$$
where $XY$ denotes the unordered pair $\{X,Y\}$. Visit <graph neighbours> in <lexicographic order> of their one-letter labels, starting at $A$. The discovery order, computed by the diagram's generator, is
$$
A,B,D,E,C,F,G.
$$
The discovery <edges> in order are $AB,BD,BE,EC,CF,FG$. They form a <rooted tree> spanning the reached <vertices>, with <root of a tree> $A$. The other <edges>, $AC$ and $EG$, remain in the original <graph> but never discover a new <vertex>. In particular, the <graph cycle> $A,B,E,C,A$ causes no repeated discovery.

\Image[depth-first-search-stack.png]
{title=<Depth-first search>: discovery <edges> and the active <call stack> on seven <vertices>}
{description=Numbers show first-discovery order. Solid <edges> form the discovery <tree>; dashed <edges> belong only to the original <graph>. The right panel shows the <call stack> from oldest call to current call, including the return from $D$ before entering $E$.}

At $D$ there is no undiscovered <graph neighbour>, so its call returns to $B$. The next call enters $E$, then $C$, then $F$, then $G$. Immediately after discovering $G$, the <call stack> is $A,B,E,C,F,G$, with $G$ on top; $D$ is still discovered but its call has finished. The maximum <call stack> depth is six, although seven <vertices> are discovered. Following the recorded <parent in a rooted tree> backwards at each step reconstructs a <graph path>; here the route from $A$ to $G$ is $A,B,E,C,F,G$, using five <edges>. <Breadth-first search> instead finds $A,B,E,G$, using three <edges>. <Depth-first search> establishes <reachability> but does not guarantee the fewest <edges>.

An explicit <LIFO stack> can replace <recursion>, but its entries and discovery rule must be specified. To reproduce this exact traversal, store one frame per active <vertex>, retaining the next position in its <adjacency list>. Advance the top frame by one <graph neighbour>; if that <vertex> is undiscovered, mark it and push its frame immediately; pop an exhausted frame. Pushing all undiscovered <graph neighbours> at once and marking them on push is a different iterative variant. Even pushing them in reverse <lexicographic order> does not generally reproduce the <parent in a rooted tree> relationships above: $C$ would already be marked while processing $A$, so $E$ could not discover $C$.

With an <adjacency list> representation, constant-cost discovery checks and frame operations, and the <graph neighbours> already ordered, <depth-first search> has <time complexity> $O(|V|+|E|)$ in <Big O notation>. Each reached <vertex> is entered once and each incident <edge> is examined at most twice in an <undirected graph>; initializing all discovery marks costs $O(|V|)$. The <call stack> has depth at most $|V|$, since no active <vertex> repeats. Discovery marks and the recorded <parent in a rooted tree> for each nonroot <vertex> also need $O(|V|)$ auxiliary <space complexity>, excluding storage for the <graph>. Sorting <adjacency lists> to obtain a chosen order is additional work. https://raw.githubusercontent.com/kevin-wayne/algs4/master/src/main/java/edu/princeton/cs/algs4/DepthFirstPaths.java[Sedgewick and Wayne, Algorithms: DepthFirstPaths discovery marks and resource bounds]{ref}

One start explores only its <connected component of a graph>. To cover a disconnected <graph>, start again at every still-undiscovered <vertex> while keeping all discovery marks; the discovery <trees> form a <forest>. <Depth-first search> is useful for <reachability>, constructing a <spanning tree> of a <connected graph>, and organizing the return steps needed by a <depth-first traversal of a tree>. For detecting a <graph cycle> in a <simple graph> that is an <undirected graph>, an <edge> to an already discovered <vertex> other than the current <parent in a rooted tree> closes a <graph cycle>; the immediate return <edge> to that <parent in a rooted tree> is not itself a <graph cycle>.

= Memoization
{parent=Algorithm}
{wiki}

<Memoization> retains a completed <function> result under a <memoization key> and returns that result when an equivalent request recurs. For a terminating <pure function>, repeated evaluation can therefore become lookup rather than repeated work. The benefit is especially striking with <recursion> and <overlapping subproblems>: a large <tree> of calls can refer to a small <directed acyclic graph> of distinct answers. The <memoization cache contract> determines whether reuse is correct; the <memoization cache lifetime> determines whether an answer is still present when wanted.

<Memoization> records computed answers, whereas a <memory cache> retains data from <computer memory>. A <CPU> <cache hit> does not by itself prevent a program from evaluating the same <function> again. <Spreadsheet dependency evaluation> adds an explicit mechanism for invalidating affected <cached cell values> after inputs change; a general <memoization> table does not discover such changes automatically.

A documented early motivation was to let programs improve their efficiency during execution through rote learning: the abstract of a 1968 paper explicitly proposes such a <programming-language> facility.<“Memo” Functions and Machine Learning by Donald Michie>[Donald Michie, “Memo” Functions and Machine Learning, Nature 218, pp. 19–22 (1968), abstract: programming-language rote learning motivated by efficiency during execution]{ref}

= Overlapping subproblems
{parent=Memoization}
{wiki}

<Overlapping subproblems> occur when several parts of a calculation request the same smaller problem. <Memoization> can share its answer if the <memoization key> identifies that problem completely. For the <Fibonacci numbers>, both $F_5$ and $F_4$ require $F_3$. In <dynamic programming>, the <dynamic programming state> plays the corresponding role of identifying a reusable continuation. Overlap explains potential savings; the <recurrence relation> and its base cases still need to be correct.

= Memoized Fibonacci evaluation
{c}
{parent=Memoization}
{title2=$F_n$}

The <Fibonacci numbers> give an exact example. For a nonnegative <integer> $n$, their <recurrence relation> is
$$
F_0=0,\qquad F_1=1,\qquad F_n=F_{n-1}+F_{n-2}\quad(n\geq2).
$$
To obtain $F_5=5$ by direct <recursion>, evaluate $F_4$ and $F_3$ separately; computing $F_4$ also evaluates $F_3$. The full call <tree> has 15 occurrences but just six distinct arguments, $0,1,2,3,4,5$. Shared dependencies form a <directed acyclic graph> because every <directed edge> goes to a strictly smaller argument. <Memoization> evaluates a distinct argument on first demand; filling values in increasing argument order is the corresponding bottom-up <dynamic programming> calculation.<Lecture 15: Recursive Algorithms (6.006 Spring 2020) by Massachusetts Institute of Technology, 6.006 course staff>[MIT 6.006 Spring 2020, Lecture 15: Recursive Algorithms, printed pp. 2–3, Fibonacci Numbers and Re-using Subproblem Solutions]{ref}

\Image[memoization-fibonacci-recursion-and-dependencies.png]
{title=Repeated calls for <Fibonacci numbers> and their shared <directed acyclic graph> of dependencies}
{description=The call <tree> contains 15 occurrences for $F_5$. The dependency <graph> contains six distinct arguments and eight <directed edges>. Equal labels have equal colors; arrows in the right panel point from a caller to the value it requires.}

Use an initially empty <hash table> `memo`, shared by every recursive call. Count even the first evaluations of the two base cases, store only completed results, evaluate the left term first, and retain all entries. The following original procedure assumes a nonnegative <integer> argument:

```
def cached_fib(n, memo):
    if n in memo:
        return memo[n]
    if n < 2:
        value = n
    else:
        value = cached_fib(n - 1, memo) + cached_fib(n - 2, memo)
    memo[n] = value
    return value
```

Every self-call must pass through the <memoization> lookup. Wrapping only the outer call while leaving inner calls uncached retains the repeated work. Test membership rather than whether the stored value is nonzero: $F_0=0$ is a valid completed result.

For cold $F_5$, the lookup arguments are $5,4,3,2,1,0,1,2,3$. The first six are absent; the last three reuse completed answers. Results are stored on return in argument order $1,0,2,3,4,5$, with values $1,0,1,2,3,5$. Thus there are nine wrapper calls, six body evaluations and four <additions>. Repeating $F_5$ with the same table takes one wrapper call and no body evaluation. Requesting $F_6$ next evaluates only its body, reuses $F_5$ and $F_4$, and stores $F_6=8$: three wrapper calls, one body evaluation and two hits.

\Image[memoization-cache-trace-and-lifetime.png]
{title=An exact <memoization> lookup trace and the effect of retaining or clearing its table}
{description=The first row records cold $F_5$ lookup order. The table records successive requests with one retained table; clearing it before the final request restores the cold counts. Calls include lookups that immediately return stored values; bodies count only first evaluations.}

The direct-call count satisfies $C_0=C_1=1$ and $C_n=1+C_{n-1}+C_{n-2}$. Its exact solution is $C_n=2F_{n+1}-1$, as substitution into this <recurrence relation> verifies. With the specified <memoization> procedure, a cold call at $n\geq2$ evaluates $n+1$ distinct bodies, makes $n-1$ <additions> and makes $2n-1$ wrapper calls. There are $n-2$ hits: each of the $n-1$ nonbase bodies issues two recursive calls, in addition to the initial call. The difference is between the number of occurrences and the number of distinct subproblems.

= Memoization arithmetic and stack costs
{parent=Memoization}

Under constant-cost lookup and <integer> <addition>, <memoized Fibonacci evaluation> has <time complexity> $O(n)$ in <Big O notation>, retaining $O(n)$ values. A <hash table> needs its own lookup-cost assumptions; an <array> indexed by $0,\ldots,n$ avoids <hash collisions> in this example. <Memoization> removes repeated bodies, but also pays for keys, lookups and retained answers. A workload without reuse can pay those costs without saving evaluations.

The <call stack> remains. Left-first <recursion> descends through arguments $n,n-1,\ldots,1$ before returning, giving $n$ simultaneously active frames for $n\geq2$. Therefore the auxiliary <space complexity> includes $O(n)$ frames as well as $O(n)$ table entries in the constant-size-value model. An iterative bottom-up <dynamic programming> calculation removes these recursive frames; retaining only the two previous <Fibonacci numbers> suffices when only the final value is wanted, but discards the table useful for later requests.

Exact <Fibonacci numbers> do not remain constant-size values. For $k\geq2$, the <recurrence relation> gives $2^{(k-2)/2}\leq F_k\leq2^{k-1}$, so the representation of $F_k$ as a <binary number> has order $k$ <bits>. With ordinary <addition> costing order $k$ <bit> operations on such operands, the $n-1$ <additions> cost order $n^2$ <bit> operations in total. Retaining all values also requires order $n^2$ <bits> of value storage, before keys and frame overhead. The linear bound counts <additions> under its stated cost model; it is not a linear bound on exact <integer arithmetic> in <bits>.<Lecture 15: Recursive Algorithms (6.006 Spring 2020) by Massachusetts Institute of Technology, 6.006 course staff>[MIT 6.006 Spring 2020, Lecture 15: Recursive Algorithms, printed p. 3, final three bullets: growing Fibonacci bit lengths and addition cost]{ref}

= Memoization cache contract
{parent=Memoization}

For a terminating <pure function>, a reusable entry must record its correct completed result, and equal <memoization keys> must imply equal results throughout the entry's <memoization cache lifetime>. Reusing that result must also preserve the behavior callers require. These conditions separate correctness from speed: a complete key can be correct even if it rarely repeats.

A procedure using <deterministic computation> can still have a required <side effect>. If a procedure returns $n^2$ and appends an audit record on every call, serving the second call from a table preserves the numerical answer but skips the second record. Likewise, if each call promises a fresh <mutable list>, returning the same stored <mutable list> changes observable sharing and allows a caller to damage later answers. Plain result reuse is unsuitable for those contracts.<Python 3.14 documentation/functools — Higher-order functions and operations on callable objects (Python 3.14 documentation)>[Python documentation, functools.lru_cache: paragraph warning against functions with side effects, distinct mutable results, or impure time/random results]{ref}

Completion matters for <recursion>. Suppose computing key $A$ needs key $B$, and computing $B$ needs $A$. A table containing only completed answers has no answer to return for the second $A$; remembering completed values does not make this <directed cycle> terminate. Marking a key `ACTIVE` before descending detects re-entry, as in <spreadsheet dependency evaluation>, but detection is not a solution of the circular equations. If computation fails, clear its active mark and do not publish an unfinished value. The example using <Fibonacci numbers> avoids this issue through a strictly decreasing argument.

The call counts above assume sequential execution and no eviction. Concurrent requests for an absent key can both begin evaluation before either publishes its result; keeping a table coherent alone does not ensure one body execution per key.<Python 3.14 documentation/functools — Higher-order functions and operations on callable objects (Python 3.14 documentation)>[Python documentation, functools.cache and functools.lru_cache: thread-safe cache updates can still allow repeated evaluation before completion]{ref}

= Memoization key
{parent=Memoization cache contract}
{title2=$K(x,c)$}

A <memoization key> identifies all information that determines a reusable answer. Write $x$ for explicit arguments and $c$ for relevant context. For a <function> $f$ and key <function> $K$, the necessary value condition is
$$
K(x,c)=K(y,d)\ \Longrightarrow\ f(x,c)=f(y,d).
$$
This implication need hold only for contexts in which the entry can be reused. The condition concerns <key equality>, not merely equality of <hash-function> outputs: a <hash table> must resolve <hash collisions> by comparing complete keys. Include the identity or version of the procedure if one table stores results for several procedures or changing implementations.

For an original toy example, let $g(n,a)=an$. Caching only by $n$ after $g(3,2)=6$ incorrectly returns $6$ for $g(3,4)$, whose answer is $12$. The pair $(n,a)$ is complete for this <function>. If $a$ is hidden in mutable configuration, either freeze that configuration for the <memoization cache lifetime>, include a reliable version in the key, or invalidate affected entries before reuse. A version is sufficient only if every relevant change updates it. Object identity alone is likewise insufficient for a <mutable list> whose contents determine the answer.

= Memoization cache lifetime
{parent=Memoization cache contract}

A <memoization cache lifetime> is the interval over which retained entries are available and valid. One table per top-level request shares recursive subproblems within that request; keeping a table between requests also allows the warm $F_5$ and incremental $F_6$ examples. Clearing it loses those savings. Evicting a correct answer can preserve correctness for a terminating <pure function>, while forcing recomputation; changing an input without invalidating an obsolete answer can break correctness.

Specify who owns the table, when context changes invalidate it, and how long keys and results occupy <computer memory>. In a concrete implementation, retained references can keep arguments and answers alive until removal or clearing.<Python 3.14 documentation/functools — Higher-order functions and operations on callable objects (Python 3.14 documentation)>[Python documentation, functools.lru_cache: cache_clear and retention of argument and return-value references until eviction or clearing]{ref} The <memoization> promise is conditional reuse of valid completed answers, not an automatic guarantee of freshness, termination or bounded <computer memory>.

= Recursion
{synonym}

<Recursion> solves a problem by invoking the same procedure on smaller instances, with base cases answered directly. For <merge sort>, an empty or one-entry <array> is already sorted, and every larger <array> is split into two shorter parts. The decreasing lengths justify termination; a self-call without a progress rule would not suffice.

A <recursive procedure> refers to itself, directly or through another procedure. A <recursive call> starts another invocation, with its own arguments and local <variables>; the caller can wait for its returned <output>. A <base case> supplies an answer without further <recursive calls>. To establish <algorithm termination>, also show that every <recursive call> progresses in a <well-founded relation>. “Smaller” means smaller in that chosen relation: argument values need not all decrease, and the arguments need not even be numbers.

<Recursion> is especially expressive when a <data structure> already decomposes into smaller structures. A <binary tree> has two child <subtrees>, so <structural recursion> can follow its shape. A short rule for each case can describe an entire traversal or computation. The distinction between a <recursive procedure> and the <recursive process> it generates helps connect that compact description to its resource use.<Structure and Interpretation of Computer Programs by Harold Abelson and others>[Structure and Interpretation of Computer Programs, second edition, §1.2.1: procedure versus process; §1.2.2: closing discussion before Counting change, hierarchical data and straightforward definitions]{ref}

= Factorial recursion and returning frames
{parent=Recursion (computer science)}
{title2=$F(0)=1,\quad F(n)=nF(n-1)$}

For a <natural number> $n$, the <factorial> satisfies $0!=1$ and $n!=n(n-1)!$ for $n\geq1$. The following description includes the zero <base case> explicitly; a negative or nonintegral <input> is outside its <precondition>:
``
F(n):
    require n is an integer and n >= 0
    if n == 0:
        return 1
    child_result = F(n - 1)
    return n * child_result
``
For $n=4$, the arguments on descent are $4,3,2,1,0$. Each positive-argument invocation postpones one <multiplication> until its <recursive call> returns. At the deepest point, the <call stack> has five <stack frames>: four suspended callers and the active zero <base case>. The invocation at zero returns $1$ to the invocation at one, rather than finishing the entire computation. Returns then give
$$
F(0)=1,\quad F(1)=1\cdot1=1,\quad F(2)=2\cdot1=2,\quad F(3)=3\cdot2=6,\quad F(4)=4\cdot6=24.
$$
A <stack frame> retains the caller's argument and where to resume. When the invocation at three receives $2$, it uses its own $n=3$, obtains $6$, and returns that value to the invocation at four. The <recursive calls> share a definition, but their local <variables> belong to separate invocations.

\Image[recursion-factorial-returning-frames.png]
{title=Factorial descent builds pending work; returning frames complete it}
{description=Original trace of $F(4)$ with <base case> $F(0)=1$. The central snapshot shows all five <stack frames> at maximum depth. Downward arrows create <recursive calls>; upward arrows carry completed answers to suspended callers. A return removes only the completed invocation's <stack frame>.}

The <natural number> measure $n$ decreases by one on every <recursive call>, so <algorithm termination> follows. For <algorithm correctness>, use <mathematical induction>: the zero <base case> returns $0!=1$; assuming the child's answer is $(n-1)!$, the caller returns $n(n-1)!=n!$. This also explains why keeping the caller's $n$ matters.

There are exactly $n+1$ invocations and $n$ <multiplications>, including one invocation and no <multiplications> when $n=0$. Ordinary execution of this <recursive process> uses at most $n+1$ active <stack frames>, hence $O(n)$ frames for $n\geq1$ in <Big O notation>. If each test, call, <subtraction> and <multiplication> is counted as constant cost, its <time complexity> is $O(n)$. That is an arithmetic-operation model: exact arbitrary-length <integer> <multiplication> has growing cost, and neither the <factorial> <output> nor every <stack frame>'s numeric contents occupies a universally fixed number of <bits>.

= Binary array sum by recursion
{parent=Recursion (computer science)}
{title2=$S(A,l,r)=\sum_{i=l}^{r-1}A_i$}

Keep an <array> $A$ unchanged, and sum entries in the half-open <integer interval> of <array indices> $[l,r)$. The <precondition> requires <integers> $0\leq l\leq r\leq\operatorname{length}(A)$ and exact, terminating <integer> <addition>. An empty range returns the <empty sum> zero; a one-entry range returns that entry. Every longer range splits at its middle <array index>:
``
S(A, l, r):
    require integer indices with 0 <= l <= r <= length(A)
    size = r - l
    if size == 0:
        return 0
    if size == 1:
        return A[l]
    middle = l + floor(size / 2)
    left_sum = S(A, l, middle)
    right_sum = S(A, middle, r)
    return left_sum + right_sum
``
For the original <array> $A=[6,-2,5,1]$, call $S(A,0,4)$. The left half returns $6+(-2)=4$, the right half returns $5+1=6$, and the original invocation returns $4+6=10$. The right half's left endpoint increases from zero to two: what decreases is range length $r-l$, not every argument. Negative entries affect the answer but do not affect <algorithm termination>.

For range length $n=r-l\geq2$, the children have lengths $\lfloor n/2\rfloor$ and $\lceil n/2\rceil$, both positive and strictly less than $n$. The <floor function> chooses the split; the <ceiling function> gives the other length. <Algorithm termination> follows by this <natural number> measure. For <algorithm correctness>, apply <mathematical induction> on $n$: the two <base cases> return the specified <sum>; for a larger range, the two disjoint child ranges cover every original <array index> exactly once, so <addition> of their correct <sums> gives the required <sum>.

For $n\geq1$, the invocation <tree> is a <full binary tree> with $n$ leaves, one per <array> entry. If $I$ is its number of nonleaf <vertices>, counting <edges> gives $2I=I+n-1$, so $I=n-1$. Thus the total invocation count is $2n-1$, and there are $n-1$ combining <additions>. Here $n=4$ gives seven calls and three combining <additions>. For $n=1$, there is one call and no combining <addition>; for $n=0$, there is also one call and no combining <addition>, but no entry leaf, so the $2n-1$ formula does not apply.

The <call stack> holds the active branch, rather than the entire invocation <tree>. Execute the left child completely before the right child, retaining the left result in the parent <stack frame>. The maximum number of active <stack frames> is $1+\lceil\log_2 n\rceil$ for $n\geq1$, and one for $n=0$. Balanced splitting therefore needs $O(\log n)$ frames for $n\geq2$, compared with the $O(n)$ frames of the <factorial> <recursive process>. Assuming constant-cost <array> access, index operations and <addition>, its <time complexity> is $O(n)$ and its auxiliary <space complexity> is $O(\log n)$ <machine words> for $n\geq2$, excluding the stored <input>. Pass the same <array> with different endpoints, rather than copying slices. These bounds require all stored indices and partial sums to fit in a constant number of <machine words>; exact unbounded <integer> <addition> and storage require a separate <bit> cost analysis.

= Well-founded progress in recursion
{parent=Recursion (computer science)}
{title2=$\mu(\text{child})<\mu(\text{parent})$}

A <base case> and a decreasing <natural number> measure work together. Check that every invocation satisfies its <precondition>, each <base case> finishes with the correct <output>, and every other invocation makes finitely many <recursive calls> with strictly smaller measure. All local work must also terminate. By <well-founded induction>, the children finish, so their caller finishes; if their answers are correct and the combination rule preserves the <postcondition>, the caller is correct too. This proves <total correctness>, not just correctness conditional on return.

Strict decrease without a lower bound is insufficient: subtracting one forever from a negative <integer> never reaches zero. Even a positive real-valued measure can decrease indefinitely, as $1,1/2,1/4,\ldots$ shows. A <well-founded relation> rules out that descent. In <structural recursion>, a proper child <subtree> of a finite <binary tree> supplies progress without numeric arguments. The proof obligation is the relation between parent and child instances, together with terminating local work and complete <base cases>.

= Base case
{parent=Recursion (computer science)}

A case answered without further <recursive calls>. Complete <base cases> are one part of an <algorithm termination> argument; the other cases must progress in a <well-founded relation>.

= Recursive call
{parent=Recursion (computer science)}

An invocation made by a <recursive procedure> of itself, directly or through another procedure. Each invocation has its own arguments and local <variables>; a returning invocation supplies an <output> to its caller.

= Divide-and-conquer algorithm
{parent=Algorithm}
{wiki}

A <divide-and-conquer algorithm> divides a problem into smaller instances, solves them using <recursion>, and combines their answers. In <merge sort>, the division makes two contiguous halves, and the <merge algorithm> combines the resulting <sorted arrays>. The important design step is finding a combination rule cheaper than solving the whole problem afresh.

Halving the <input> is only one part of the design. The number of <recursive calls> and the work outside those calls determine whether the smaller instances actually save time. <Divide-and-conquer combination cost> keeps these quantities separate; the <divide-and-conquer product ledger> shows how an algebraic identity changes the number of required calls in <Karatsuba multiplication>.

For <algorithm correctness>, specify the meaning of each returned answer, prove the <base cases>, and show that combining correct smaller answers gives the required <output>. <Induction> then proves correctness, provided every <recursive call> progresses towards a <base case>. The combination rule must reconstruct everything the caller needs: two sorted halves alone are not a <sorted array>, and four digit blocks alone are not their <integer> product.

= Divide-and-conquer combination cost
{parent=Divide-and-conquer algorithm}
{title2=$T(n)=aT(n/2)+g(n)$}

The combination cost is the work needed to reconstruct an answer from the returned smaller answers. In a <time complexity> calculation, also count partitioning the <input>, preparing arguments, and other work outside <recursive calls>. Write their total as $g(n)$ for a size-$n$ call. For an ideal balanced <divide-and-conquer algorithm> making $a$ calls of size $n/2$, the <recurrence relation> is
$$
T(1)=c_0,\qquad T(n)=aT(n/2)+g(n)\quad(n>1),
$$
where $a$ is a fixed positive <integer> and $c_0>0$ is the <base case> cost. Take $n=2^k$, a <power of two>, so the size becomes one after exactly $k$ divisions. This is a model of total sequential work: all $a$ smaller calls contribute, even if a machine could run some simultaneously.

At level $j$, there are $a^j$ calls, each of size $n/2^j$. Expanding the <recurrence relation> gives the exact identity
$$
T(n)=a^k c_0+\sum_{j=0}^{k-1}a^j g(n/2^j).
$$
The first term counts the <base cases>; the <sum> stops before their level because $g$ describes work in nonterminal calls. This separates depth, number of calls, and local work. <Merge sort> has two smaller calls and a linear <merge algorithm>, giving $T(n)=2T(n/2)+O(n)=O(n\log n)$ in <Big O notation>. The MIT notes derive this by summing equal work across levels, and contrast it with the same two-way split followed by quadratic local work.<6.006 Introduction to Algorithms, Fall 2011 by Massachusetts Institute of Technology, 6.006 course staff/Lecture 3: Insertion sort, merge sort>[6.006 Introduction to Algorithms, Fall 2011, Lecture 3: slides 32–44, recurrence and equal work per level; slide 46, quadratic local work]{ref}

\Image[divide-and-conquer-combination-work-levels.png]
{title=The same halving tree can have linear or quadratic work at each call}
{description=Original exact cost models with $n=16$, two children per nonterminal call, and one unit per <base case>. For local work $g(s)=s$, every internal level costs 16 and the total is 80. For $g(s)=s^2$, internal levels cost 256, 128, 64, 32 and the total is 496. The tree shows instance sizes; the ledger counts work rather than execution order.}

For the first constructed model, set $a=2$, $c_0=1$ and $g(s)=s$. Every internal level costs $2^j(n/2^j)=n$, while the leaves cost $n$. Thus $T(n)=n\log_2 n+n$, giving $T(16)=80$. If the same split instead has $g(s)=s^2$, then the <finite geometric series> gives
$$
T(n)=n+n^2\sum_{j=0}^{k-1}2^{-j}=2n^2-n,
$$
so $T(16)=496$. The root alone already costs $n^2$ in this second model. Smaller arguments do not eliminate expensive reconstruction. These are stipulated operation counts, rather than measured running times or exact <merge sort> instruction counts.

<Binary search> has a different saving: after its comparison, only one half remains a candidate. With constant-cost indexed <array> access and comparisons, its worst-case <time complexity> satisfies an upper <recurrence relation> $T(n)\leq T(\lfloor n/2\rfloor)+C$ for $n\geq1$, with $T(0)=c_0$. There is one continuing branch, rather than two. At most $\lfloor\log_2 n\rfloor+1$ nonempty candidate ranges are inspected for $n\geq1$. Copying the retained half into a fresh <array> on every step would add linear work at that step and lose this logarithmic bound. The shrinking range and its representation both matter.

= Divide-and-conquer product ledger
{parent=Divide-and-conquer algorithm}

Splitting two <integers> in <positional notation> gives $x=aq+b$ and $y=cq+d$, where $q=B^m$ shifts a block by $m$ <numeral digits> in fixed <radix> $B\geq2$. The <distributive property> gives
$$
xy=acq^2+(ad+bc)q+bd.
$$
Computing $ac,ad,bc,bd$ separately needs four block <multiplications>. Merely halving the operands therefore gives an ideal <recurrence relation> $F(n)=4F(n/2)+O(n)$, still with quadratic <time complexity>. The <Karatsuba three-product identity> instead computes $ac$, $bd$ and $(a+b)(c+d)$, recovering the middle <coefficient> by two <subtractions>. The MIT notes present precisely this four-product versus three-product distinction.<6.006 Introduction to Algorithms, Fall 2011 by Massachusetts Institute of Technology, 6.006 course staff/Lecture 11: Numerics I>[6.006 Introduction to Algorithms, Fall 2011, Lecture 11: Numerics I, printed pp. 4–5, High Precision Multiplication and Karatsuba's Method]{ref}

For an original small example, multiply $47$ by $63$. Set $B=q=10$, $a=4$, $b=7$, $c=6$, $d=3$. Four separate block products would give $ac=24$, $ad=12$, $bc=42$, $bd=21$. The three-product calculation is
$$
\begin{aligned}
u&=ac=24,&v&=bd=21,&w&=(a+b)(c+d)=11\cdot9=99,\\
h&=w-u-v=99-24-21=54,\\
47\cdot63&=100u+10h+v=2400+540+21=2961.
\end{aligned}
$$
The crucial reuse is that $u$ and $v$ supply the outer <coefficients> and also remove the unwanted terms from $w$. There is no need to compute $ad$ and $bc$ separately. Expanding $w=ac+ad+bc+bd$ proves the identity. <Induction> extends it to <Karatsuba multiplication> once each smaller block product is correct and <Karatsuba recursion termination> supplies decreasing sizes and complete <base cases>.

\Image[divide-and-conquer-four-versus-three-products.png]
{title=Four block products or three: the exact ledger for $47\cdot63$}
{description=The left ledger computes both cross products separately. The right ledger reuses $ac=24$ and $bd=21$ to recover their sum as $99-24-21=54$. Both reconstructions yield $2961$. Counts refer to block <multiplication> calls at this split; the extra <numeral digit> in $4+7=11$ prevents interpreting all three as single-digit products.}

The operation model matters. Let $n$ count <numeral digits> in fixed <radix> $B$, and count single-digit <multiplication>, <addition>, <subtraction> and copying as constant-cost operations. The nonrecursive work on size-$n$ operands is $O(n)$: it includes forming sums, positional shifts and <Karatsuba carry handling>. Treating an arbitrarily large <integer> <multiplication> as one operation would hide the very saving being studied. The coefficients $24,54,21$ above must be shifted and added; concatenating them does not give $2961$.

In the ideal equal-half model, <Karatsuba multiplication> has $K(n)=3K(n/2)+O(n)$. At depth $j$ its additional work is at most a constant times $n(3/2)^j$, and its leaf count is $3^k=n^{\log_2 3}$ for $n=2^k$. A <geometric series> gives $K(n)=O(n^{\log_2 3})$, where $\log_2 3\approx1.585$. Four recursive products would instead give $4^k=n^2$ leaves. Saving one block product repeatedly changes the exponent, even though the combination requires extra <addition> and <subtraction>.

For the literal sum-based version, each operand sum can occupy one extra <numeral digit>. Its worst-case upper <recurrence relation> is $K(n)\leq3K(\lceil n/2\rceil+1)+Cn$ for a nondecreasing cost envelope, above a fixed <base case> threshold of at least three digits. <Karatsuba digit-operation cost> proves that this extra digit preserves the exponent; <Karatsuba operand splitting> handles odd lengths and leading zero padding. For signed <integers>, apply the nonnegative procedure to their <absolute values> and restore the sign. The small ledger establishes an exact identity, while <Karatsuba practical crossover> explains why it alone cannot predict a speedup for two-digit operands.

= Sorting algorithm
{parent=Algorithm}
{wiki}
{title2=$B_0\leq B_1\leq\cdots\leq B_{n-1}$}

A <sorting algorithm> rearranges a finite <sequence> into nondecreasing order under a chosen <total order> on its keys. Its <output> must contain every <input> entry exactly once, including repetitions: producing ordered values is insufficient if entries are lost. <Merge sort> is one such <algorithm>; <stable sorting> adds a requirement about equal keys.

Sorting creates reusable structure: equal <sort keys> become adjacent, and a <sorted array> supports <binary search>. However, an <algorithm correctness> check must establish both <sortedness> and <sorting permutation preservation>. Replacing every entry by the smallest key can produce ordered keys while destroying the original data. <Stable sorting> imposes a third condition when equal <sort keys> occur: retain their arrival order.

For example, take complete <sorting records> $(2,A),(1,B),(2,C),(1,D)$, with the first component as the <sort key> and the letter as associated data. A correct <output> is $(1,B),(1,D),(2,A),(2,C)$. The <sort keys> are ordered, every complete <sorting record> remains, and the equal-key pairs keep $A$ before $C$ and $B$ before $D$. The <output> $(1,D),(1,B),(2,C),(2,A)$ satisfies <sortedness> and <sorting permutation preservation>, but fails <stable sorting>. The <output> $(1,B),(1,B),(2,A),(2,A)$ has the right <multiset> of <sort keys> but loses $C,D$ and duplicates $A,B$; it fails <sorting permutation preservation> of complete <sorting records>.

To express <stable sorting> precisely, label every <input> occurrence by its original position, even when two complete <sorting records> have identical contents. Let $p(i)$ be the <output> position of the occurrence originally at position $i$. Besides <sortedness> and <sorting permutation preservation>, require
$$
i<j\ \text{and}\ k(A_i)=k(A_j)\quad\Longrightarrow\quad p(i)<p(j).
$$
Here $k$ is the <sort key> <function>. Sorting by the pair $(k(A_i),i)$ under <lexicographic order> gives the same order as <stable sorting> by $k$: the original position breaks ties without discarding associated data. For a two-field ordering, first apply <stable sorting> by the secondary <sort key>, then apply <stable sorting> by the primary <sort key>. The second pass retains the secondary order within each group of equal primary <sort keys>. For instance, $(2,B),(1,C),(2,A),(1,A)$ first becomes $(2,A),(1,A),(2,B),(1,C)$ by letter, then $(1,A),(1,C),(2,A),(2,B)$ by number.

= Sort key
{parent=Sorting algorithm}
{title2=$k(A_i)$}

A <sort key> is the value extracted from a complete entry to determine its ordering. Model extraction as a <function> $k$ into a <total order>; compare $k(A_i)$ and $k(A_j)$, while moving the complete entries. Ordering <sorting records> by an age field does not also compare their names. Repeated <sort keys> are allowed, so this induces equal-key groups even when the complete <sorting records> differ. Keep the <sort key> <function> and the comparison rule fixed throughout a sort; inconsistent comparisons need not admit any sorted result.

= Sorting record
{parent=Sort key}

A complete entry comprising a <sort key> together with any associated data. In $(2,A)$, the <sort key> is $2$ and $A$ stands for the associated data or an identity label. <Sorting permutation preservation> concerns these complete entries, rather than only their extracted <sort keys>.

= Sortedness
{parent=Sorting algorithm}
{title2=$k(B_i)\leq k(B_{i+1})$}

For an <output> <sequence> $B$ of length $n$, <sortedness> means
$$
k(B_i)\leq k(B_{i+1})\qquad(0\leq i<n-1)
$$
under the chosen <total order> on <sort keys>. Its <transitivity> also gives $k(B_i)\leq k(B_j)$ whenever $i<j$. An empty <sequence> and a one-entry <sequence> satisfy <sortedness> without any adjacent comparison. For longer <sequences>, checking adjacent pairs suffices; checking only the first and last <sort keys> does not. For example, $(1,3,2,4)$ passes an endpoint comparison but fails <sortedness> at $3,2$. <Sortedness> alone says nothing about which <input> entries survived.

= Sorting permutation preservation
{parent=Sorting algorithm}
{title2=$B_i=A_{\pi(i)}$}

The <output> of a <sorting algorithm> must be a <permutation> of the complete <input> <sequence>. For equal lengths $n$, require a <permutation> $\pi$ of $\{0,\ldots,n-1\}$ such that
$$
B_i=A_{\pi(i)}\qquad(0\leq i<n).
$$
Equivalently, the <input> and <output> have the same <multiset> of complete entries: each entry has the same multiplicity. Equality of the underlying <sets> is insufficient; $(1,1,2)$ and $(1,2,2)$ have the same <set> of values and the same length but different <multisets>. When tracking occurrences rather than contents, retain original identity labels to check that each one is moved exactly once. A swap preserves this <multiset> automatically; an overwrite need not.

= Insertion sort
{parent=Sorting algorithm}
{wiki}

<Insertion sort> grows a sorted prefix of an <array> one entry at a time. In the adjacent-swap version, start with position $i=1$, compare its current <sort key> with the preceding <sort key>, and swap the complete <sorting records> only when the right <sort key> is strictly smaller. Continue leftward until no swap is needed or the entry reaches position zero; then process original position $i+1$. A tie stops the pass. This is the strict comparison and exchange rule in the authored implementation.<Insertion.java by Robert Sedgewick and others>{ref}

Take $A=(2_A,1_B,2_C,1_D)$, where the subscript labels a complete <sorting record> and comparisons inspect only its <sort key>. Starting from index zero, the complete key-comparison trace is:

|| Comparison
|| Right <sort key> smaller than left?
|| Action
|| <Array> after the action

| 1, insert position $1$
| $1_B<2_A$: yes
| Swap positions $0,1$.
| $(1_B,2_A,2_C,1_D)$

| 2, insert position $2$
| $2_C<2_A$: no
| Stop this pass on a tie.
| $(1_B,2_A,2_C,1_D)$

| 3, insert position $3$
| $1_D<2_C$: yes
| Swap positions $2,3$.
| $(1_B,2_A,1_D,2_C)$

| 4, continue leftward
| $1_D<2_A$: yes
| Swap positions $1,2$.
| $(1_B,1_D,2_A,2_C)$

| 5, continue leftward
| $1_D<1_B$: no
| Stop this pass on a tie.
| $(1_B,1_D,2_A,2_C)$

\Image[sorting-stable-insertion-compare-swap-trace.png]
{id=sorting-stable-insertion-compare-swap-trace}
{title=<Insertion sort>: five <sort key> comparisons and three complete-entry swaps}
{description=Each row after the <input> shows the state after one comparison. Orange cells mark an adjacent swap; green cells mark a stopping tie. Identity letters are not compared. Both equal-key groups retain their <input> order, demonstrating <stable sorting>.}

The <loop invariant> is that, before pass $i$, positions $0,\ldots,i-1$ satisfy <sortedness> and contain precisely the entries originally in that prefix. Moving the next entry left through strictly larger <sort keys> extends that prefix, and every swap retains <sorting permutation preservation>. Equal-key entries never cross, giving <stable sorting>. Each leftward step decreases the position, and each completed pass increases the prefix length, so the <algorithm> terminates.

With constant-cost key comparisons and swaps, reverse-ordered distinct <sort keys> cause $1+2+\cdots+(n-1)=n(n-1)/2$ comparisons and swaps. Thus worst-case <time complexity> is $O(n^2)$ in <Big O notation>. An already sorted <array> needs only $n-1$ key comparisons for $n\geq1$ and no swaps. The adjacent-swap version uses constant auxiliary <space complexity>. Small or nearly sorted <arrays> can therefore make <insertion sort> useful despite its quadratic worst case.

= Comparison-based sorting
{synonym}

A <comparison sort> learns the ordering of <sort keys> only by comparing pairs. The keys are otherwise opaque: their numeric values, digits or encodings cannot choose an <array> index or a branch. It may move complete <sorting records> and retain previous answers. <Merge sort> and the adjacent-swap <insertion sort> are <comparison sorts>; <counting sort> and <radix sort> exploit additional information.

= Comparison sorting lower bound
{parent=Comparison sort}
{title2=$C_{\max}(n)\geq\lceil\log_2(n!)\rceil$}

Any deterministic <comparison sort> correct for all orders of $n$ distinct <sort keys> needs at least $\lceil\log_2(n!)\rceil$ comparisons on some <input>. Here $n!$ is a <factorial>, $\log_2$ a <logarithm>, and the brackets denote the <ceiling function>. This is a worst-case requirement, not a requirement on every <input>.<Open Data Structures: An Introduction by Pat Morin/11.1 Comparison-Based Sorting>[Theorem 11.5: deterministic comparison-tree lower bound]{ref}

For three distinct <sort keys>, the diagram has one leaf for each possible ordering of the original entries $a,b,c$. Some paths need two comparisons, others three; two comparisons cannot distinguish all six orders.

\Image[sorting-three-distinct-keys-comparison-decision-tree.png]
{id=sorting-three-distinct-keys-comparison-decision-tree}
{title=A comparison <decision tree> distinguishes the six orders of three distinct <sort keys>}
{description=Each internal node tests the <sort keys> of two fixed original entries. A leaf gives the order in which their complete <sorting records> must be emitted. There are $3!=6$ leaves and maximum depth three. The diagram assumes distinct <sort keys>, so no equality branch is needed.}

For the proof outline, represent adaptive comparisons by a <binary tree>: distinct <sort keys> give only two outcomes per comparison. A leaf fixes an <output> <permutation>; one leaf cannot correctly handle two different strict orders. Hence there must be at least $n!$ leaves. Maximum depth $h$ permits at most $2^h$ leaves, so $2^h\geq n!$ gives the bound. Even a three-way comparator has only two reachable outcomes on this distinct-key family.

The growth follows without a precise approximation to the <factorial>. At least $\lfloor n/2\rfloor$ of its factors are at least $n/2$, so for $n\geq2$,
$$
\log_2(n!)\geq\lfloor n/2\rfloor\log_2(n/2).
$$
The brackets denote the <floor function>. This gives a constant times $n\log n$ lower bound for large $n$, matching the worst-case comparison growth of <merge sort>.

Distinct <sort keys> are essential to the $n!$ counting argument. Identical <sort keys> do not create $n!$ different strict orders. If all <sort keys> coincide, <stable sorting> returns the arrival order. This does not remove the worst-case bound for a <comparison sort> required to handle arbitrary distinct-key <inputs>.

= Counting sort
{parent=Sorting algorithm}
{wiki}
{title2=$T(n,K)=O(n+K)$}

<Counting sort> uses <integer> <sort keys> in $\{0,\ldots,K-1\}$ directly as indices into an <array> of counts. Constant-cost counting and indexing give $O(n+K)$ <time complexity> in <Big O notation>. To retain complete <sorting records>, cumulative counts locate their <output> ranges; filling each range from its end while scanning the <input> backwards gives <stable sorting>. Emitting bare <sort keys> from counts would discard associated data. The $K$ term matters when the key range is large.<Open Data Structures: An Introduction by Pat Morin/11.2 Counting Sort and Radix Sort>[Open Data Structures: An Introduction by Pat Morin; Theorem 11.7 and stability]{ref}

For an original worked example, take $n=7$ complete <sorting records> and $K=4$ possible <integer> <sort keys>:
$$
A=\bigl((2,\mathrm A),(0,\mathrm B),(2,\mathrm C),(1,\mathrm D),(0,\mathrm E),(3,\mathrm F),(2,\mathrm G)\bigr).
$$
The letters label the associated data, and are never compared. Both <input> and <output> <array indices> start at zero, so their valid positions are $0,\ldots,6$; the count <array> has <array indices> $0,\ldots,3$. <Stable sorting> must produce
$$
B=\bigl((0,\mathrm B),(0,\mathrm E),(1,\mathrm D),(2,\mathrm A),(2,\mathrm C),(2,\mathrm G),(3,\mathrm F)\bigr).
$$
The equal-<sort key> groups retain $\mathrm B,\mathrm E$ and $\mathrm A,\mathrm C,\mathrm G$ in arrival order. <Counting sort prefix ranges> explain where those groups belong; <stable record placement in counting sort> explains how to fill them without losing that order or the complete <sorting records>.

= Counting sort prefix ranges
{parent=Counting sort}
{title2=$[S_k,P_k)$}

For $n\geq0$ <sorting records> with <integer> <sort keys> in $\{0,\ldots,K-1\}$, where $K\geq1$, let $c_k$ count the <input> occurrences of <sort key> $k$. Define two <prefix sums>:
$$
S_k=\sum_{h=0}^{k-1}c_h,\qquad P_k=\sum_{h=0}^{k}c_h=S_k+c_k.
$$
The <empty sum> gives $S_0=0$. Here $c_k,S_k,P_k$ are counts of <sorting records>. Exactly $S_k$ <sorting records> have smaller <sort keys>, so the <output> positions for <sort key> $k$ form the half-open <integer interval>
$$
\{j\in\mathbb Z:S_k\leq j<P_k\}=[S_k,P_k)\cap\mathbb Z.
$$
Its right endpoint $P_k$ is excluded: the last occupied <array index> is $P_k-1$ when $c_k>0$.<Open Data Structures: An Introduction by Pat Morin/11.2 Counting Sort and Radix Sort>[Open Data Structures: An Introduction by Pat Morin; §11.2.1 Counting Sort, paragraphs after Figure 11.7: running sums count keys at most k and determine the output block]{ref}

For the seven-<sorting record> example, the frequency <array>, inclusive cumulative count <array>, and start <array> are
$$
c=(2,1,3,1),\qquad P=(2,3,6,7),\qquad S=(0,2,3,6).
$$
Thus <sort keys> zero, one, two and three occupy the <integer intervals> $[0,2)$, $[2,3)$, $[3,6)$ and $[6,7)$, respectively. In particular, the three <sorting records> with <sort key> two belong at <array indices> three, four and five. The inclusive cumulative count $P_2=6$ counts all six <sorting records> with <sort keys> at most two; six is the exclusive endpoint, not the final position of a <sorting record> with <sort key> two.

= Stable record placement in counting sort
{parent=Counting sort}
{title2=$E_k\gets E_k-1,\quad B_{E_k}\gets A_i$}

Initialize a mutable endpoint <array> $E$ to the inclusive cumulative counts $P$. Scan <input> <array indices> $i=n-1,n-2,\ldots,0$. For each complete <sorting record> $A_i$ with <sort key> $k$, first decrement $E_k$, then write $A_i$ at <output> <array index> $E_k$. This is equivalent to writing at the old endpoint minus one and then decrementing the endpoint.<Open Data Structures: An Introduction by Pat Morin/11.2 Counting Sort and Radix Sort>[Open Data Structures: An Introduction by Pat Morin; §11.2.1 Counting Sort, final scan paragraph and stability paragraph after Theorem 11.7]{ref}

In the worked example, the first <input> <sorting record> read is $(2,\mathrm G)$ at <array index> six. Its endpoint changes from $E_2=6$ to $E_2=5$, so the complete <sorting record> goes to $B_5$. Next, $(3,\mathrm F)$ changes $E_3$ from seven to six and goes to $B_6$. Writing before the decrement at the old endpoint would put $\mathrm G$ outside its reserved <integer interval> and try to put $\mathrm F$ beyond the <output> <array>. All seven writes are:
$$
\begin{array}{c|c|c|c|c}
\text{step}&\text{input index }i&A_i& E_k\text{ before}\to\text{after}&\text{output index}\\\hline
1&6&(2,\mathrm G)&6\to5&5\\
2&5&(3,\mathrm F)&7\to6&6\\
3&4&(0,\mathrm E)&2\to1&1\\
4&3&(1,\mathrm D)&3\to2&2\\
5&2&(2,\mathrm C)&5\to4&4\\
6&1&(0,\mathrm B)&1\to0&0\\
7&0&(2,\mathrm A)&4\to3&3
\end{array}
$$
Each endpoint changes only when a <sorting record> with its own <sort key> is placed. Consequently, $E_2$ stays at five through the placements of $\mathrm F,\mathrm E,\mathrm D$ before dropping to four for $\mathrm C$.

{title=A backward <input> scan gives forward order among equal <sort keys>}
{description=Original complete trace of the seven-<sorting record> example. Each row shows the endpoint decrement and resulting <output> <array>; the newly written complete <sorting record> is dark. Both <input> and <output> <array indices> start at zero. The final order is $\mathrm B,\mathrm E,\mathrm D,\mathrm A,\mathrm C,\mathrm G,\mathrm F$.}

Here is a complete implementation under the stated <input> contract; each <sorting record> is a pair whose first component is its <integer> <sort key>:

```
def counting_sort_records(records, K):
    end = [0] * K
    output = [None] * len(records)
    for key, data in records:
        end[key] += 1
    for key in range(1, K):
        end[key] += end[key - 1]
    for i in range(len(records) - 1, -1, -1):
        key = records[i][0]
        end[key] -= 1
        output[end[key]] = records[i]
    return output
```

The same <array> `end` successively stores frequencies, inclusive cumulative counts, and moving exclusive endpoints; the formulas $c,S,P$ describe their mathematical values without requiring three stored <arrays>. The write copies the complete <sorting record>, including its associated data. In particular, two occurrences of an identical pair still cause two separate writes.

For a short <algorithm correctness> proof, let $r_k$ be the number of already placed <sorting records> with <sort key> $k$. A <loop invariant> is
$$
E_k=P_k-r_k,\qquad [S_k,E_k)\text{ is unfilled},\qquad [E_k,P_k)\text{ is filled}.
$$
All <integer intervals> here mean <output> <array indices>. Initially $r_k=0$, so each whole reserved <integer interval> is unfilled. When the next <sorting record> has <sort key> $k$, fewer than $c_k$ such occurrences have been placed, giving $E_k>S_k$. Decrementing selects a fresh slot inside its reserved <integer interval>. At termination, $r_k=c_k$ and $E_k=S_k$: every <output> slot has been filled exactly once with a complete <input> occurrence. The disjoint, increasing <sort key> ranges establish <sortedness>, while the fresh-slot property establishes <sorting permutation preservation>.

For <stable sorting>, take two <input> occurrences with equal <sort keys> at <array indices> $i<j$. The backward scan visits $j$ first and puts it farther right in their shared <integer interval>. When $i$ is visited, the endpoint has decreased at least once, so its <output> position is smaller. Thus their original order survives. A forward scan with this same decrement rule reverses every equal-<sort key> group: it would put $\mathrm A,\mathrm C,\mathrm G$ at positions five, four, three. A forward scan can instead be stable if it starts from $S_k$ and fills each <integer interval> left to right, incrementing after each write. The scan direction and endpoint convention must agree.

Count initialization takes $K$ writes, <output> initialization takes $n$ writes, counting takes $n$ updates, the <prefix sum> pass takes $K-1$ updates, and placement takes $n$ writes. Hence <time complexity> and auxiliary storage are $O(n+K)$ in <Big O notation>, assuming constant-cost <sort key> access, <integer> arithmetic, <array> indexing and complete <sorting record> movement. Large records can instead be represented by constant-size references.<Open Data Structures: An Introduction by Pat Morin/11.2 Counting Sort and Radix Sort>[Open Data Structures: An Introduction by Pat Morin; §11.2.1 Counting Sort, auxiliary counter and output arrays, loop-cost discussion and Theorem 11.7]{ref}

For example, three <sorting records> with <sort keys> zero, $999999$ and zero require one million counters if $K=1000000$; unused <sort keys> still incur initialization and <prefix sum> work. The bound is therefore linear in the <input> length only when $K=O(n)$. Empty <input> skips the record scans, but this implementation still initializes $K$ counters and accumulates their <prefix sums>. For nonempty <input>, counting all $n$ records and filling their ranges gives a concrete termination argument.

Direct <sort key> indexing is a different operation from a binary comparison. The <comparison sorting lower bound> concerns <comparison sorts>; <counting sort> uses its restricted <integer> <sort keys> as <array indices>. Its small-$K$ speed is particularly useful for categorical numerical labels and for each <stable sorting> pass of <radix sort>: the reserved <integer intervals> turn group sizes into exact destinations.

= Radix sort
{parent=Sorting algorithm}
{wiki}
{title2=$T(n,d,R)=O(d(n+R))$}

<Radix sort> sorts encoded <sort keys> a digit at a time. Its least-significant-digit version uses <stable sorting> on each successive digit, often by <counting sort>. For $d$ digits with $R$ possible values each, it takes $O(d(n+R))$ <time complexity> in <Big O notation>, assuming constant-cost digit extraction and indexing. <Stable sorting> retains the ordering established by earlier digits when a later digit ties. Both digit access and the direct indexing in <counting sort> lie outside the <comparison sort> model, so these bounds do not contradict the <comparison sorting lower bound>.<Open Data Structures: An Introduction by Pat Morin/11.2 Counting Sort and Radix Sort>[Open Data Structures: An Introduction by Pat Morin; Theorem 11.8]{ref}

= Least-significant-digit radix sort
{parent=Radix sort}

A least-significant-digit radix sort processes <numerical digits> from smallest to largest <place value>. Fix <integers> $R\ge2$ and $d\ge1$, and take $n$ complete <sorting records> whose <sort keys> satisfy $0\le k<R^d$. Use exactly $d$ positions in <positional notation> with <radix> $R$, including leading zeros. At pass $j=0,\ldots,d-1$, apply a <stable digit sort> to the current <array> using
$$
\delta_j(k)=\left\lfloor\frac{k}{R^j}\right\rfloor\bmod R.
$$
The <floor function> selects the integer <quotient>, and the <remainder> selects the current <numerical digit>. Move the complete <sorting record>, including its associated data. There are exactly $d$ passes, so this procedure terminates even for an empty <array>. The <radix sort suffix invariant> supplies its <algorithm correctness> argument.

For an original <input>, let the letters identify the attached data:
$$
(314_A,027_B,305_C,042_D,217_E,005_F,127_G,040_H).
$$
Here $R=10$, $d=3$, and leading zeros only align <place values>; $005$ represents the <integer> five. The exact pass ledger is:
$$
\begin{array}{c|llllllll}
\text{input}&314_A&027_B&305_C&042_D&217_E&005_F&127_G&040_H\\
\text{units}&040_H&042_D&314_A&305_C&005_F&027_B&217_E&127_G\\
\text{tens}&305_C&005_F&314_A&217_E&027_B&127_G&040_H&042_D\\
\text{hundreds}&005_F&027_B&040_H&042_D&127_G&217_E&305_C&314_A
\end{array}
$$
After the units pass, the <numerical digits> are $0,2,4,5,5,7,7,7$. The ties retain $C$ before $F$ and $B$ before $E$ before $G$. This <array> is not yet ordered by its whole <integer> <sort keys>: $314$ still precedes $305$. After the tens pass, the two-position suffixes are $05,05,14,17,27,27,40,42$. In particular, $217_E$ now precedes $027_B$: their tens <numerical digits> differ, so <stable sorting> does not require retaining their previous order. The hundreds pass produces the final <sorted array>, with all attached letters preserved.

= Radix sort suffix invariant
{parent=Least-significant-digit radix sort}
{title2=$s_p(k)=k\bmod R^p$}

After $p$ passes, $0\le p\le d$, the <array> is in nondecreasing order of $s_p(k)=k\bmod R^p$, the <integer> represented by its $p$ lowest <numerical digits>. Equivalently it is ordered by the <tuple> $(\delta_{p-1}(k),\ldots,\delta_0(k))$ under <lexicographic order>, with the most significant processed <numerical digit> first. Among equal suffixes it retains the original order of the complete <sorting records>.

The <loop invariant> has a simple <mathematical induction> proof. Before any pass, $s_0(k)=k\bmod1=0$ for every <sort key>, so the original <array> satisfies it. Suppose it holds after $p$ passes. The next <stable digit sort> puts smaller $\delta_p$ groups first and preserves the existing $s_p$ order within each tie. Since
$$
s_{p+1}(k)=R^p\delta_p(k)+s_p(k),\qquad 0\le s_p(k)<R^p,
$$
the new <array> is ordered by $s_{p+1}$. Equal new suffixes have equal current <numerical digits> and equal old suffixes, so their original order is also preserved. Every pass is a <permutation> of complete <sorting records>, establishing <sorting permutation preservation>. At termination $p=d$, the assumption $k<R^d$ gives $s_d(k)=k$: the invariant becomes whole-key <sortedness>, together with <stable sorting>.

= Stable digit sort
{parent=Radix sort}

A <stable digit sort> applies <stable sorting> to complete <sorting records> using one specified <numerical digit> of their encoded <sort keys>. <Counting sort> can supply it; <stable record placement in counting sort> moves records without discarding their associated data. Stability concerns equal current <numerical digits>, even when the full <sort keys> differ. This is the information-preservation step in <least-significant-digit radix sort>.<Open Data Structures: An Introduction by Pat Morin/11.2 Counting Sort and Radix Sort>[Open Data Structures: An Introduction by Pat Morin; §11.2.1, associated-data and stability paragraphs; §11.2.2, least-significant passes and correctness paragraph after Figure 11.8]{ref}

An original two-record counterexample exposes the need for the tie rule. Start with $(42_A,41_B)$ at width three. A units pass gives $(041_B,042_A)$. Both tens <numerical digits> are four. A deliberately unstable tens pass may reverse their tie and return $(042_A,041_B)$: it is sorted by the tens <numerical digit>, yet its two-position suffixes $42,41$ are decreasing. The final stable hundreds pass sees two zeros and keeps this wrong order. <Sorting permutation preservation> still holds, but <sortedness> fails. Stability in the tens pass would have retained the units information.

With <counting sort> as the <stable digit sort>, each pass initializes $R$ counters, counts $n$ current <numerical digits>, constructs their <prefix sums>, and places $n$ complete <sorting records>. Thus each pass costs $O(n+R)$, and $d$ passes cost $O(d(n+R))$ in <Big O notation>. Reuse the counters and two <arrays> of record references between passes: auxiliary <space complexity> is $O(n+R)$, rather than $O(d(n+R))$. Assume constant-cost <numerical digit> extraction, counter <arithmetic>, <array> indexing and record-reference movement; the bound counts these operations, not the cost of copying arbitrarily large payloads or performing arbitrary-precision <integer arithmetic>.

The benefit is avoiding a counter for every possible whole <sort key>: width $d$ has $R^d$ possibilities, while each pass needs only $R$ counters. A larger <radix> reduces the number of passes for a fixed key range but enlarges the counter <array>. The <comparison sorting lower bound> does not apply to these direct <array indices>; they reveal more than a two-way comparison. Nor does fixing $R$ make $d$ disappear: growing key width still increases work.

= Radix sort key encoding
{parent=Radix sort}

An encoding for <radix sort> must make the intended <total order> of <sort keys> agree with the <lexicographic order> of its fixed-width <numerical digit> <tuples>. The <positional notation> for bounded nonnegative <integers> has this property. At the most significant differing position $m$, a one-unit <numerical digit> difference contributes $R^m$, while all lower positions together contribute at most
$$
(R-1)\sum_{j=0}^{m-1}R^j=R^m-1.
$$
This <geometric series> shows why lower <numerical digits> cannot reverse that comparison. Leading zero padding works here because it preserves <place values> and the represented <integer>.

For signed <integers> in a known <integer interval> $L\le x\le U$, encode $e(x)=x-L$ and choose $d$ with $U-L<R^d$. This <order-preserving function> is also <injective>: $x<y$ exactly when $e(x)<e(y)$. For $-8\le x\le7$, the four-<bit> encodings of $-8,-3,-1,0,4,7$ are $0000,0101,0111,1000,1100,1111$ after adding eight. Restore the original signed <sort keys> when displaying the complete <sorting records>; the encoding need not replace their data. Sorting the unsigned values of raw <two's complement> <bit> patterns would put nonnegative <integers> before negative ones, so their representation alone is not this ordered encoding.

For variable-length <strings>, first specify the <alphabet> order and whether a proper prefix precedes its extensions. As an original construction, use $a<b$, let every <string> have length at most three, encode $a$ as one and $b$ as two, and append zeros to width three. Zero is reserved for an end marker strictly below every real symbol. The <strings> $\varepsilon,a,aa,ab,b$ encode as $000,100,110,120,200$ in <radix> three, which preserves their <lexicographic order>. A differing real symbol decides the comparison; at a prefix boundary, the shorter <string>'s zero comes before the extension's one or two. Left padding would instead encode $b$ as $002$ and $aa$ as $011$, reversing $aa<b$. Padding raw <bytes> with zero also fails if zero is an allowed data symbol: distinct <strings> can then receive the same encoding. A reserved end marker and an explicit symbol ordering are essential; byte order alone does not establish a desired human text order.

= Stable sorting
{parent=Sorting algorithm}

<Stable sorting> preserves the original relative order of entries with equal keys. The entries may carry different names or other information even when their keys coincide. For example, sorting records $(2,\mathrm{Ada}),(1,\mathrm{Bo}),(2,\mathrm{Cy})$ by the numerical key gives $(1,\mathrm{Bo}),(2,\mathrm{Ada}),(2,\mathrm{Cy})$: Ada remains before Cy. This is useful when a previous ordering contains information worth retaining, such as arrival order among equally ranked requests.

= Merge sort
{parent=Sorting algorithm}
{wiki}
{title2=$T(n)=O(n\log n)$}

<Merge sort> is a <divide-and-conquer algorithm> that sorts a finite <array> by splitting it into contiguous halves, sorting each half using <recursion>, and combining the two <sorted arrays> with the <merge algorithm>. An empty or one-entry <array> is returned immediately. For length $n\geq2$, put the first $\lfloor n/2\rfloor$ entries on the left and the remaining $\lceil n/2\rceil$ on the right; the brackets are the <floor function> and <ceiling function>. Always choose the left head on equal keys to obtain <stable sorting>. This is the split, sort, combine structure taught in the MIT lecture notes.<6.006 Introduction to Algorithms, Fall 2011 by Massachusetts Institute of Technology, 6.006 course staff/Lecture 3: Insertion sort, merge sort>[6.006 Introduction to Algorithms, Fall 2011 by Massachusetts Institute of Technology, 6.006 course staff; MIT 6.006 (2011), lecture 3: merge sort]{ref}

Take the concrete <input> <array>
$$
A=(7,2_a,5,2_b,9,1,4,3).
$$
The tags identify the entries originally at indices $1$ and $3$, counting from zero. Both keys are $2$; the tags are never compared. Reading downward in the figure follows the splits, then the returned <sorted arrays>. Arrows show dependencies; the level layout groups independent calls rather than giving their chronological execution order.

Thus this precise version makes $4+6+7=17$ head comparisons and, ignoring identity tags, returns $(1,2,2,3,4,5,7,9)$.

The elegance of <merge sort> is that it creates exactly the structure its next step needs: two smaller <sorted arrays> make the larger ordering inexpensive. Once the whole <array> is sorted, equal keys are adjacent and <binary search> can serve repeated queries. <Stable sorting> also retains information that the keys alone do not express. If the left-half <merge algorithm> instead takes the right head on the $2_a=2_b$ tie, it returns $(2_b,2_a,5,7)$; the keys are sorted but <stable sorting> has failed.

For <time complexity>, assume each key comparison, entry access and entry copy has constant cost. The <merge algorithm> processes $n$ entries in $O(n)$ time. In <Big O notation>, the resulting <recurrence relation> is
$$
T(0),T(1)=O(1),\qquad T(n)=T(\lfloor n/2\rfloor)+T(\lceil n/2\rceil)+O(n)\quad(n\geq2).
$$
For $n=2^k$, the balanced levels contain $n$ entries each and there are $k=\log_2 n$ returning levels. Each costs $O(n)$, so the worst-case <time complexity> is $O(n\log n)$. For arbitrary $n$, there are at most $\lceil\log_2 n\rceil$ returning levels, each processing at most $n$ entries, giving the same bound. The worst-case number of head comparisons is also $O(n\log n)$. Here $\log_2$ is the base-two <logarithm>. The MIT notes give this level-by-level analysis for <merge sort>.https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-spring-2020/6d1ae5278d02bbecb5c4428928b24194_MIT6_006S20_lec3.pdf[MIT 6.006 (2020), lecture 3, page 5: merge sort analysis]{ref}

The conventional <array> implementation uses a reusable buffer of $n$ entries for the <merge algorithm>, together with $O(\log n)$ pending calls for <recursion>. Its auxiliary <space complexity> is therefore $O(n)$, beyond the original <array>. This bound describes that implementation. A <linked list> permits a <merge algorithm> that reconnects existing nodes; its storage accounting differs from copying <array> entries into a buffer.

For a short <algorithm correctness> outline, the empty and one-entry base cases are sorted. Assuming <recursion> correctly sorts both shorter halves, the <merge algorithm> returns all their entries in order. Equal keys within a half keep their relative order by the same argument applied to the smaller call; across halves, every left entry originally preceded every right entry, so taking left first preserves <stable sorting>. Both half-lengths decrease for $n\geq2$, establishing termination.

= Merge algorithm
{parent=Algorithm}
{wiki}
{title2=$C(m,n)\leq m+n-1\quad(m,n\geq1)$}

The <merge algorithm> combines two finite sorted <sequences> under the same <total order>, retaining every entry exactly once. Keep a position at the first unconsumed entry, or "head", of each <input>. While both heads exist, compare their keys, append the smaller head to the <output>, and advance only that head's position. On equality take the left head. Once either <sequence> is exhausted, append the other remainder without further key comparisons. Empty <inputs> therefore require no head comparisons. The MIT notes illustrate this two-head combination step.<6.006 Introduction to Algorithms, Fall 2011 by Massachusetts Institute of Technology, 6.006 course staff/Lecture 3: Insertion sort, merge sort>[6.006 Introduction to Algorithms, Fall 2011 by Massachusetts Institute of Technology, 6.006 course staff; MIT 6.006 (2011), lecture 3: merging sorted arrays]{ref}

For example, the <merge algorithm> applied to $(1,4,7)$ and $(2,3,8,9)$ returns $(1,2,3,4,7,8,9)$:

\Image[merge-two-sorted-sequences.png]
{title=Five head comparisons in the <merge algorithm>}
{description=Orange heads are chosen and arrows lead to the next <output> entry. The compared head pairs are (1,2), (4,2), (4,3), (4,8) and (7,8). The left <sequence> then runs out; append (8,9) without further key comparisons.}

The head pairs $(1,2)$, $(4,2)$, $(4,3)$, $(4,8)$ and $(7,8)$ select $1,2,3,4,7$ respectively. After the fifth comparison the left <sequence> is empty, so $(8,9)$ is appended. Seven entries are written, but only five head comparisons occur: tests for exhaustion and appending the remainder are separate operations. This distinction makes the example's count smaller than the bound $3+4-1=6$.

For nonempty <inputs> of lengths $m,n$, each head comparison consumes exactly one entry. After $m+n-1$ such removals at most one entry remains, so both heads cannot still exist. Hence the <merge algorithm> uses at most $m+n-1$ head comparisons. The bound can be attained: $(1,3,5)$ and $(2,4,6,7)$ require six head comparisons before the left <sequence> is exhausted. With constant-cost comparisons, access and copying, writing all $m+n$ entries gives <time complexity> $O(m+n)$ in <Big O notation>. Writing a separate <output> <array> needs $m+n$ entry slots; the two positions require only constant additional storage.

The <merge algorithm> is useful whenever two already ordered collections must become one: it reads each <input> only forwards. This works with <arrays> and <linked lists>, without needing access to arbitrary middle positions. Choosing left on ties preserves each <input>'s internal order and places equal left entries before equal right entries, which is the combination rule needed for <stable sorting> in <merge sort>.

The <loop invariant> behind <algorithm correctness> is that the emitted prefix is sorted, contains exactly the consumed entries, and every emitted key is at most every unconsumed key. Each sorted <sequence> has its smallest remaining key at its head, so the smaller of the two heads is safe to append. The invariant survives each removal; when one <sequence> ends, the other sorted remainder is safe to append in full. Each comparison removes an entry, so termination follows from the finite <input> lengths.

= Binary search
{parent=Algorithm}
{wiki}

<Binary search> finds a target $x$ in a <sorted array> $A$ by inspecting the middle of the remaining candidate range. If the middle entry is smaller than $x$, every entry to its left is also too small; if larger, every entry to its right is too large. One comparison therefore rules out many entries. Equal entries are allowed; this version returns any matching index, without promising the first occurrence.

Use indices starting at zero and inclusive endpoints $L,R$. Initially $L=0$, $R=n-1$, where $n$ is the <array> length. While $L\leq R$, choose
$$
m=L+\left\lfloor\frac{R-L}{2}\right\rfloor.
$$
The brackets denote the <floor function>. Compare $A_m$ with $x$: return $m$ on equality; set $L=m+1$ if $A_m<x$; otherwise set $R=m-1$. If $L>R$, report absence. The updates exclude the already inspected middle entry. This also handles an empty <array>, whose initial endpoints are $0,-1$. Sedgewick and Wayne specify a <sorted array> as <input> and return a matching index or $-1$ for absence.https://algs4.cs.princeton.edu/code/javadoc/edu/princeton/cs/algs4/BinarySearch.html[Sedgewick and Wayne: BinarySearch API]{ref}

For a fully worked example, take the <sorted array>
$$
A=(2,5,8,12,16,23,38,56,72,91,104,130,160,205,260).
$$
Search for $x=23$:

|| Step
|| Candidate indices
|| Middle index and value
|| Consequence

| 1
| $0\ldots14$
| $m=7$, $A_7=56$
| $23<56$: retain $0\ldots6$.

| 2
| $0\ldots6$
| $m=3$, $A_3=12$
| $23>12$: retain $4\ldots6$.

| 3
| $4\ldots6$
| $m=5$, $A_5=23$
| Return index $5$.

For $x=24$, the first two steps agree. Next $24>23$ retains only index $6$; inspecting $A_6=38$ sets $R=5$. Now $L=6>5=R$, so the answer is "absent" after four comparisons.

The <loop invariant> is: the <array> stays sorted, $0\leq L\leq R+1\leq n$, and every index containing $x$ lies between $L$ and $R$. It holds initially. The <sorted array> property justifies each exclusion. Returning on equality gives a match; an empty candidate range implies absence. Crucially, this <loop invariant> allows $x$ to be absent from the beginning.

For a nonempty range of size $s=R-L+1$, an unsuccessful comparison leaves at most $\lfloor s/2\rfloor$ candidates. Thus sizes satisfy $s_k\leq\lfloor n/2^k\rfloor$ after $k$ unsuccessful comparisons. This proves termination and, for $n\geq1$, at most $\lfloor\log_2 n\rfloor+1$ middle-entry comparisons. The final singleton still needs inspection: $n=1$ requires one comparison, not zero. = Karatsuba multiplication
{parent=Algorithm}
{c}
{wiki}

<Karatsuba multiplication> is a <divide-and-conquer algorithm> for <multiplication> of <integers>. Splitting each operand into two blocks seems to require four smaller products; the <Karatsuba three-product identity> recovers the two cross terms together from just three products. Repeating that saving through <recursion> changes the <time complexity> from quadratic to $O(n^{\log_2 3})$, where $n$ counts digits in a fixed <positional notation>. The exponent is about $1.585$: the benefit comes from the <algorithm>, even though each splitting step needs more <addition> and <subtraction>.

The <Karatsuba worked multiplication> below computes $1234\cdot5678=7{,}006{,}652$ using $12\cdot56$, $34\cdot78$, and $46\cdot134$. The last operand already shows why “half-size” needs care: <Karatsuba carry handling> and <Karatsuba recursion termination> account for the extra digit. <Karatsuba digit-operation cost> states the operation model; <Karatsuba practical crossover> explains why the asymptotic saving alone does not select a useful threshold.

The original 1962 paper presents a <binary numeral system> automaton construction: its Theorem 2 and proof reduce <multiplication> to taking <squares of numbers>, then reduce a larger <square of a number> to three smaller <squares of numbers>. Its footnote explicitly addresses the extra digit in a sum of halves. The sequential <time complexity> analysis below uses a different operation model from that paper's automaton size and depth bounds, including its <Boolean circuit> realization without feedback.<Multiplication of many-digital numbers by automatic computers by A. Karatsuba and Yu. Ofman>[Karatsuba and Ofman, Multiplication of many-digital numbers by automatic computers, original Russian article, 1962, pp. 293–294: Theorem 2, its proof, and the footnote on p. 294]{ref}

= Karatsuba operand splitting
{parent=Karatsuba multiplication}
{c}
{title2=$x=aB^m+b,\quad y=cB^m+d$}

Fix an <integer> base $B\geq2$. Let $x,y\geq0$ have at most $n$ digits in <positional notation>, treating zero as one digit. For $n>1$, set $m=\lceil n/2\rceil$ using the <ceiling function>, and $q=B^m$. <Euclidean division> gives
$$
a=\lfloor x/q\rfloor,\quad b=x-aq,\qquad c=\lfloor y/q\rfloor,\quad d=y-cq,
$$
where $0\leq b,d<q$ and $0\leq a,c<B^{n-m}$. The <floor function> selects the high block; the remainder selects the low block. Both operands must use the same $q$, including when their actual digit lengths differ.

For odd $n$, the low block has $m$ digit positions and the high block has $n-m=m-1$. Leading zero padding aligns a shorter operand without changing its <integer> value. Padding to a power-of-two length is optional: the split itself works for every $n$. If power-of-two padding is used, the padded length is less than twice the original length, so it changes only a constant factor in the <asymptotic analysis>.

= Karatsuba three-product identity
{parent=Karatsuba multiplication}
{c}
{title2=$xy=acB^{2m}+((a+b)(c+d)-ac-bd)B^m+bd$}

Compute exactly three smaller products,
$$
p_2=ac,\qquad p_0=bd,\qquad p_s=(a+b)(c+d).
$$
The <distributive property> gives $p_s=ac+ad+bc+bd$, so the cross coefficient is $h=p_s-p_2-p_0=ad+bc$. Recombine by
$$
xy=p_2q^2+hq+p_0,\qquad q=B^m.
$$
The saving is that $ad$ and $bc$ are never separately multiplied. Multiplying a digit block by $q$ or $q^2$ shifts its position in <positional notation>; it does not require another general <integer> <multiplication>. <Addition> of the shifted results still requires <Karatsuba carry handling>.

= Karatsuba worked multiplication
{parent=Karatsuba multiplication}
{c}

Use <decimal expansion>, $B=10$, $n=4$, $m=2$, and $q=100$. The <Karatsuba operand splitting> is $1234=12\cdot100+34$, $5678=56\cdot100+78$. The <Karatsuba three-product identity> gives
$$
\begin{aligned}
p_2&=12\cdot56=672,\\
p_0&=34\cdot78=2652,\\
p_s&=(12+34)(56+78)=46\cdot134=6164,\\
h&=6164-672-2652=2840,\\
xy&=672\cdot10000+2840\cdot100+2652=7{,}006{,}652.
\end{aligned}
$$
The third product has a three-digit operand. A small-input base case can evaluate these three products directly, or a smaller threshold can continue <recursion>. Either choice preserves the identity; only the operation count changes.

The same <Karatsuba operand splitting> handles $123\cdot45$: choose $n=3$, $m=2$, and write $123=1\cdot100+23$, $45=0\cdot100+45$. Then $p_2=0$, $p_0=1035$, $p_s=24\cdot45=1080$, and $h=45$, giving $4500+1035=5535$. A zero high block and unequal lengths require no new algebraic rule.

= Karatsuba carry handling
{parent=Karatsuba multiplication}
{c}

The blocks in the <Karatsuba three-product identity> are <integers>, not single digits: $p_0$ can need $2m$ positions and $h$ can exceed $q-1$. Concatenating the displayed blocks therefore fails. Accumulate their shifted values with ordinary <addition>, normalizing each digit position by <Euclidean division>: a coefficient $v$ becomes the digit $v\bmod B$, with carry $\lfloor v/B\rfloor$ passed to the next position. <Subtraction> likewise propagates borrows. Although $h\geq0$ for these nonnegative <integers>, intermediate digitwise <subtraction> can still borrow.

In the four-digit <Karatsuba worked multiplication>, grouping by base $q=100$ gives unnormalized coefficients $[672,2840,2652]$, written from high to low. Normalize from the right: $2652=26\cdot100+52$; $2840+26=2866=28\cdot100+66$; $672+28=700=7\cdot100+0$. The final groups are $[7,00,66,52]$, yielding $7{,}006{,}652$. The zero group must retain its two positions.

Since $a,b,c,d<B^m$, their sums are less than $2B^m\leq B^{m+1}$ and can need $m+1$ digits. Allocate that extra digit before the third recursive product; discarding it can change the answer. The GMP manual describes this sum growth and uses a difference-based form to avoid it.<GNU MP 6.3.0 manual/Karatsuba Multiplication>[GNU MP 6.3.0 manual, §15.1.2 Karatsuba Multiplication: sum-based middle product can exceed k limbs; absolute differences and their signs]{ref}

= Karatsuba recursion termination
{parent=Karatsuba multiplication}
{c}

For the sum-based <Karatsuba three-product identity>, a safe fixed base-case threshold is three digits or more. Return zero directly if either operand is zero; at or below the threshold, use ordinary digit-by-digit <multiplication>. Otherwise split by the maximum current operand length and invoke <Karatsuba multiplication> on $(a,c)$, $(b,d)$, and $(a+b,c+d)$.

Each recursive operand has at most $\lceil n/2\rceil+1$ digits. This is strictly less than $n$ for $n\geq4$, proving termination. A rule stopping only at one digit does not supply this guarantee: in base two, $3=11_2$ splits into $1,1$, whose sum is $2=10_2$, still two digits. An implementation must choose a sufficient threshold or explicitly handle such nonshrinking calls. Leading zero padding must not be repeatedly added in a way that defeats the decreasing size measure.

For signed <integers>, multiply absolute values with the same nonnegative procedure and restore the sign afterwards. This changes the representation bookkeeping, rather than the three-product identity.

= Karatsuba digit-operation cost
{parent=Karatsuba multiplication}
{c}
{title2=$T(n)=O(n^{\log_2 3})$}

Count a fixed-base digit <addition>, <subtraction>, digit copy, or single-digit <multiplication> as constant cost. Base $B$ stays fixed as $n$ grows; an entire arbitrary-length <integer> <multiplication> is not one constant-cost step. With this model, splitting, sum formation, shifts and recombination require $O(n)$ digit operations. Ordinary digit-by-digit <multiplication> forms $n^2$ digit products for two $n$-position operands. The GMP base-case description uses this rectangular product arrangement.<GNU MP 6.3.0 manual/Basecase Multiplication>[GNU MP 6.3.0 manual, §15.1.1 Basecase Multiplication: rectangular cross-products and O(NM) cost]{ref}

The ideal equal-half <recurrence relation> is
$$
T(n)=3T(n/2)+O(n).
$$
For $n=2^k$, level $j$ has $3^j$ calls of size $n/2^j$. If each internal call incurs exactly $\alpha$ times its size in additional digit work, that level contributes $\alpha n(3/2)^j$. There are $3^k=n^{\log_2 3}$ leaves. The <geometric series> of internal work is
$$
\alpha n\sum_{j=0}^{k-1}(3/2)^j=2\alpha(3^k-2^k).
$$
Thus fixed positive leaf cost plus this internal work grows on the order of $n^{\log_2 3}$. In <Big O notation>, $T(n)=O(n^{\log_2 3})$. Removing one of four products at every level matters much more than saving just one at the root.

The literal sum-based implementation instead admits the upper bound
$$
T(n)\leq3T(\lceil n/2\rceil+1)+Cn
$$
for a nondecreasing worst-case cost envelope above a fixed base-case threshold. The extra digit does not change the exponent: since $\lceil n/2\rceil+1\leq n/2+3/2$, subtracting three from the size makes each child's adjusted size at most half its parent's. Stop this comparison at any fixed threshold greater than three; its <recursion> depth is $\log_2 n+O(1)$ and the level-work sum is bounded by the same <geometric series> up to constant factors. Exact call counts can depend on carries, zero shortcuts and the threshold, so they need not equal the ideal $3^j$ at each depth.

= Karatsuba practical crossover
{parent=Karatsuba multiplication}
{c}

<Karatsuba digit-operation cost> explains eventual scaling, while a practical base-case threshold depends on the costs of <addition>, <subtraction>, copying and function calls relative to small <integer> <multiplication>. Using $M(n)=An^2+Dn+E$ for a base-case cost, one Karatsuba level costs $3M(n/2)+Fn+G$: the quadratic coefficient falls to $3A/4$, but the linear contribution includes $3Dn/2+Fn$. Small operands can therefore cost more despite the smaller exponent. This comparison and the effect of implementation improvements on the threshold are described in the GMP manual.<GNU MP 6.3.0 manual/Karatsuba Multiplication>[GNU MP 6.3.0 manual, §15.1.2 Karatsuba Multiplication: final paragraphs comparing M(N) and K(N), and effects of base-case speedups on thresholds]{ref}

The plotted crossover belongs only to the stipulated constants in its caption; its ordinary-method curve counts digit products alone, while the Karatsuba curve includes the chosen internal overhead. Selecting a threshold for real software requires measuring the actual implementation on its intended machine. With base $B=2^w$ for a fixed machine digit width $w$, the same analysis counts machine digits; it does not establish a universal crossover in decimal digits, <bits>, or elapsed time.

= Randomized algorithm
{parent=Algorithm}
{wiki}

A randomized algorithm makes some choices using random bits.

For a fixed <input>, the random <bits> can change the path taken by a <randomized algorithm>, its <output>, or its running time. Specify the distribution of those choices and which guarantee is required: <one-sided error> permits mistakes of only one kind, whereas <ZPP> requires a correct answer and bounds the expected running time. <Polynomial identity testing> makes this distinction concrete: choosing different <field> elements changes whether a nonidentity is detected.

A <uniform distribution on a finite set> must be implemented faithfully. To choose uniformly from $\{0,1,2,3,4\}$ using fair <independent> <bits>, read three <bits> as a number from zero to seven, discard five through seven, and repeat until a permitted value appears. Each retained value has the same chance. Taking the three-bit number modulo five instead would give zero, one and two twice as many preimages as three and four, invalidating a calculation that assumes equal chances.

Derandomization converts a randomized construction or algorithm into a deterministic one while preserving its desired guarantee. The <method of conditional probabilities> does this by maintaining a computable <conditional expectation> until all choices are fixed.

= Method of conditional probabilities
{parent=Derandomization}
{wiki}

= Method of conditional expectations
{synonym}

The method of conditional probabilities turns an <expected value> guarantee into a deterministic construction. For a maximization <objective function>, fix one choice at a time, always keeping the <conditional expectation> of the final value at least as large as before. Once every choice is fixed, that <conditional expectation> is the actual value. The useful ingredient is a way to evaluate the <conditional expectations> efficiently.

No actual random choices are needed during this construction. The <probability distribution> describes hypothetical completions used in the analysis; the algorithm compares their <conditional expectations> and commits deterministically. For <maximum cut>, this converts the <random cut lower bound> into a <cut of a graph> containing at least half the <edges>. A <maximum cut> can still be larger, as the <conditional expectations cut example> shows.

= Conditional expectation choice invariant
{parent=Method of conditional probabilities}
{title2=$q_{i+1}\geq q_i$}

Let $Z=Z(X_1,\ldots,X_n)$ be a real-valued <objective function> of finitely many choices, with finite <expected value>. Suppose a prefix $P=(X_1=x_1,\ldots,X_i=x_i)$ has positive <probability>. Write $q(P)=\mathbb E[Z\mid P]$. If the next choice is a fair <bit>, the <law of total expectation> gives
$$
q(P)=\frac{q(P,0)+q(P,1)}2.
$$
At least one child is at least this average. Choose a child with the larger value, using a fixed rule for ties. The resulting <loop invariant> is $q(P)\geq\mathbb E Z$. At a complete assignment $x$, there is only one completion left, so $q(x)=Z(x)$ and therefore $Z(x)\geq\mathbb E Z$.

For a biased choice or more than two possibilities, use the corresponding weighted average:
$$
q(P)=\sum_{a:\,p_a>0}p_aq(P,a),\qquad p_a=\mathbb P(X_{i+1}=a\mid P).
$$
Some positive-<probability> child is at least the weighted average. For minimization, choose a child at most the current <conditional expectation> and reverse the invariant. The averaging identity is the same in both directions.<Discrete Probability by Jeff Erickson>[Jeff Erickson, Discrete Probability, §1.2.2, printed pp. 6–7: conditional expectation decomposition and linearity; authorship stated on the author's Algorithms notes page]{ref}

The word "probabilities" in the method's name also covers an <indicator random variable> for an undesirable outcome: keeping its <conditional expectation>, which is its <conditional probability>, strictly below one eventually forces that indicator to be zero. Optimizing an ordinary numerical <objective function> is the <method of conditional expectations> formulation used below.

= Conditional expectations for maximum cut
{parent=Method of conditional probabilities}

Let $G=(V,E)$ be a finite undirected <simple graph>, with $n=|V|$ <vertices> and $m=|E|$ <edges>. A <cut of a graph> assigns each <vertex> a label zero or one; an <edge> crosses precisely when its endpoints have different labels. Its size is the number of crossing <edges>. A <maximum cut> maximizes that size.

For the analysis, assign <independent> fair <bits> $X_v$ to the <vertices>. For each <edge> $uv$, the <indicator random variable> $I_{uv}=\mathbf1_{\{X_u\ne X_v\}}$ has <expected value> $1/2$: exactly two of the four equally likely endpoint assignments cross. Thus <linearity of expectation> gives the <random cut lower bound>:
$$
C=\sum_{uv\in E}I_{uv},\qquad \mathbb E C=\sum_{uv\in E}\frac12=\frac m2.
$$
<Linearity of expectation> does not require the <indicator random variables> to be <independent>. What matters here is the stipulated distribution of the endpoint <bits>.

= Conditional expectation cut formula
{parent=Conditional expectations for maximum cut}
{title2=$q(P)=f(P)+u(P)/2$}

For any partial assignment $P$, let $f(P)$ count <edges> whose two endpoints are already fixed on opposite sides, and let $u(P)$ count <edges> with at least one unassigned endpoint. Under the remaining <independent> fair <bits>,
$$
q(P)=\mathbb E[C\mid P]=f(P)+\frac{u(P)}2.
$$
An <edge> with fixed equal labels contributes zero; fixed unequal labels contribute one. If one endpoint is unassigned, its fair <bit> disagrees with the fixed label with <probability> $1/2$. If both endpoints are unassigned, their <independent> fair <bits> disagree with <probability> $1/2$ as well. Count each unresolved <edge> once, even when both endpoints are unassigned.

Process <vertices> in a fixed order. Evaluate the <conditional expectation cut formula> after setting the next label to zero and after setting it to one; retain the larger value, choosing zero on ties. The <conditional expectation choice invariant> ensures the final <cut of a graph> has size at least $m/2$. This is a deterministic <approximation algorithm> for <maximum cut>.<CS 4820: Algorithms, Spring 2011/Lecture notes on randomized approximation algorithms>[CS 4820: Algorithms, Spring 2011; Cornell CS 4820, Lecture notes on randomized approximation algorithms, 2 May 2011, §1.1.2, printed pp. 2–3: conditional expectations, Algorithms 1–2 and the half-total-edge-weight guarantee; no individual byline stated]{ref}

= Conditional expectations algorithm cost
{parent=Conditional expectations for maximum cut}

Directly scanning all $m$ <edges> to evaluate each child of each of $n$ choices takes $O(nm+n)$ elementary operations, in <Big O notation>. There is a faster implementation. When assigning <vertex> $v$, let $d_0$ and $d_1$ count its already assigned <graph neighbours> labelled zero and one. Contributions from <edges> not incident to $v$ are unchanged, and contributions from <edges> to unassigned <graph neighbours> stay $1/2$ for either choice. Therefore
$$
q(P,v=0)-q(P,v=1)=d_1-d_0.
$$
Choose zero if $d_1\geq d_0$, otherwise one: put $v$ on the side with fewer already assigned <graph neighbours>. With <adjacency lists>, scanning each <vertex>'s list once costs $O(n+m)$ operations overall and uses $O(n+m)$ storage including the <graph>. These bounds count operations on labels and counters that fit in machine words of $O(\log(n+m+2))$ <bits>. Multiplying the <conditional expectation cut formula> by two also permits exact integer comparisons without rounding.

If $\operatorname{OPT}$ is the size of a <maximum cut>, then $\operatorname{OPT}\leq m$. The constructed <cut of a graph> thus has size at least $m/2\geq\operatorname{OPT}/2$, an <approximation ratio> of $1/2$ in the maximization convention. The five-versus-six example illustrates the gap between this guarantee and exact optimization.

For a general <randomized algorithm>, the averaging proof alone does not establish efficient <derandomization>. One needs a polynomial number of commitments, an efficient way to find a suitable child at each step, and manageable representations and evaluation costs for the relevant <conditional expectations>. Those evaluations can themselves be hard. Enumerating all completions verifies this small example, but would take exponentially many assignments as $n$ grows. The <polynomial-time algorithm> here comes from the local <conditional expectation cut formula>, not from that enumeration.

= One-sided error
{parent=Randomized algorithm}

A randomized decision algorithm has one-sided error when one answer is always correct and only the other answer can be mistaken.

The guarantee concerns each fixed <input>, with <probability> taken over the choices of the <randomized algorithm>. Always state which answer is protected. In <polynomial identity testing>, call an <input> positive when its <polynomial> is identically zero, and let acceptance mean claiming an identity. Then the possibilities are:

|| Actual <polynomial>
|| Accept: claim identity
|| Reject: claim nonidentity

| Identically zero
| Always correct; every trial accepts.
| Impossible with exact <polynomial evaluation>.

| Nonzero
| Possible mistake if the chosen point is a zero.
| Always correct; the point is a witness.

Thus a zero <polynomial evaluation> can leave uncertainty, but a nonzero <polynomial evaluation> settles the question. An error bound for a fixed nonzero <polynomial> is not the <conditional probability> that a particular accepted <input> is an identity; that latter question would need a distribution on the <inputs> as well.

In <computational complexity theory>, a <polynomial-time algorithm> with this orientation and false acceptance <probability> at most $1/2$ establishes membership in <co-RP>. Reversing the question to ask whether the <polynomial> is nonzero gives the <RP> orientation: negative instances are always rejected. The <random evaluation test for a polynomial identity> explains the required <field>, <total degree>, sampling and evaluation assumptions.

= Error reduction for a randomized algorithm
{parent=Randomized algorithm}

Independent repetitions reduce a randomized algorithm's error probability while preserving polynomial running time.

The combining rule depends on the error orientation. For <one-sided error> with false acceptance <probability> at most $p<1$, reject as soon as any trial rejects and accept only if every trial accepts. For $k$ <independent> trials on the same fixed negative <input>, false acceptance has <probability> at most $p^k$. The protected positive <inputs> still always accept. If false rejection is the possible mistake instead, accept as soon as any trial accepts. This uses the decisive answer rather than a majority vote.

For constant $p<1$, $k$ grows only logarithmically in $1/\varepsilon$ to achieve error at most $\varepsilon$. A polynomial number of trials preserves a <polynomial-time algorithm>'s running-time bound. Independence matters: repeating one answer, or evaluating at the same random point each time, supplies no new evidence. The <independent repetition of a polynomial identity test> gives an exact $25$-outcome example.

= Polynomial identity testing
{parent=Randomized algorithm}
{wiki}

Polynomial identity testing asks whether a polynomial represented implicitly, such as by an arithmetic circuit or a remainder computation, is the zero polynomial.

Here zero means that every <coefficient> vanishes after collecting equal <monomials> in the <polynomial ring>. Testing equality of two <polynomials> $A,B$ amounts to testing $P=A-B$ for zero. An <arithmetic circuit> can permit cheap <polynomial evaluation> even when expanding all <monomials> is expensive. The <random evaluation test for a polynomial identity> exploits this: one nonzero value disproves the <polynomial identity>, while a known <total degree> limits how often a nonzero <polynomial> can evade detection.<CPSC 536N: Randomized Algorithms/Lecture 9: Polynomial Identity Testing by the Schwartz-Zippel Lemma>[CPSC 536N: Randomized Algorithms; Lecture 9: Polynomial Identity Testing by the Schwartz-Zippel Lemma, §1: formal zero means all coefficients vanish; representations and evaluation access]{ref}

For example, for an <integer> $n\ge1$, $\prod_{i=1}^n(1+x_i)$ has $2^n$ distinct <monomials>, one for each <subset> of the $n$ <variables>. Its factored expression needs only $n$ <additions> and $n-1$ <multiplications> for one <polynomial evaluation>. Evaluating the compact expression avoids creating its expanded list of <coefficients>. The saving is especially attractive in many <variables>; it does not make a zero result into a proof of identity.

= Polynomial identity testing over a finite field
{parent=Polynomial identity testing}

Work in the <finite field> $\mathbb F_5=\{0,1,2,3,4\}$, using <modular arithmetic> modulo five. Consider the two original <polynomial> examples
$$
F(x)=(x+1)^2-x^2-2x-1,\qquad G(x)=(x-1)(x-2).
$$
The <distributive property> gives $(x+1)^2=x^2+2x+1$, so all <coefficients> of $F$ cancel: $F$ is identically zero. In contrast, $G=x^2-3x+2=x^2+2x+2$ in this <finite field>, with nonzero leading <coefficient>. Its <roots of a polynomial> are exactly one and two: a product in a <field> is zero only if a factor is zero.

The complete <polynomial evaluations>, displayed as representatives modulo five, are
$$
\begin{array}{c|ccccc}
a&0&1&2&3&4\\\hline
F(a)&0&0&0&0&0\\
G(a)&2&0&0&2&1
\end{array}.
$$
In particular, $G(3)=(3-1)(3-2)=2$ is a nonzero witness, which disproves identity without examining other points. At one or two, a zero value fails to reveal that $G$ is nonzero. A <random variable> $a$ with a <uniform distribution on a finite set> $\mathbb F_5$ hits those two <polynomial roots> with <probability> $2/5$.

{title=Exact evaluations distinguish a zero polynomial from a nonzero polynomial with two roots}
{description=Every element of the <finite field> $\mathbb F_5$ is shown. The upper row always accepts the identity $F=0$. In the lower row, the two orange zero values falsely accept $G=0$; the three blue nonzero values correctly reject it. These are all possible outcomes, not sampled frequencies.}

A crucial limit appears with $H(x)=x^5-x$. Its <coefficients> make it a nonzero <polynomial> of <polynomial degree> five in $\mathbb F_5[x]$, yet direct <polynomial evaluation> gives zero at all five <field> elements: the values before reduction are $0,0,30,240,1020$, all divisible by five. Thus $H$ induces the same <polynomial function> as the zero <polynomial>. Any number of trials restricted to $\mathbb F_5$ will falsely accept this identity. This is compatible with the <Schwartz-Zippel lemma>: the ratio of <polynomial degree> to sampling-set size is $5/5=1$, which gives no useful guarantee.

When a <polynomial>'s representation permits <polynomial evaluation> over a larger <field extension>, a larger sampling <set> can restore the useful degree ratio. Access only to the induced <polynomial function> on the original <finite field> cannot distinguish $H$ from zero.<CPSC 536N: Randomized Algorithms/Lecture 9: Polynomial Identity Testing by the Schwartz-Zippel Lemma>[CPSC 536N: Randomized Algorithms; Lecture 9: Polynomial Identity Testing by the Schwartz-Zippel Lemma, §1.4: formal nonzero polynomials can vanish everywhere on a finite field; extension-field evaluations need a suitable representation]{ref}

= Random evaluation test for a polynomial identity
{parent=Polynomial identity testing}
{title2=$\mathbb P(P(a_1,\ldots,a_n)=0)\le d/|S|$}

Let $P$ be a nonzero <multivariate polynomial> over a <field> $K$, with <total degree> at most $d\ge0$. Choose a nonempty <finite set> $S\subseteq K$. For <independent random variables> $a_1,\ldots,a_n$, each with a <uniform distribution on a finite set> on $S$, the <Schwartz-Zippel lemma> gives
$$
\mathbb P\bigl(P(a_1,\ldots,a_n)=0\bigr)\le\min\{1,d/|S|\}.
$$
Nonzeroness is essential; the zero <polynomial> always evaluates to zero. The <total degree> sums exponents within each <monomial>, rather than taking their maximum: $x^2y^3+y$ has <total degree> five. The <field> need not be finite, but $S$ must be finite. The estimate reduces error only when $d/|S|<1$.<CMPT 710 and CMPT 407 - Computational Complexity - Fall 2007/CMPT 710 - Complexity Theory: Lecture 18>[CMPT 710 and CMPT 407 - Computational Complexity - Fall 2007; CMPT 710 - Complexity Theory: Lecture 18, §3.1, pp. 3–4: Lemma 4 and its inductive proof]{ref}

The proof begins with the <root bound for a polynomial>. For several <variables>, write $P=\sum_{j=0}^m Q_j(x_1,\ldots,x_{n-1})x_n^j$, with $Q_m\ne0$. The <total degree> of $Q_m$ is at most $d-m$. By <induction>, $Q_m$ vanishes with <probability> at most $(d-m)/|S|$. Otherwise the remaining univariate <polynomial> has at most $m$ <polynomial roots>. Adding the two contributions gives $d/|S|$.<CMPT 710 and CMPT 407 - Computational Complexity - Fall 2007/CMPT 710 - Complexity Theory: Lecture 18>[CMPT 710 and CMPT 407 - Computational Complexity - Fall 2007; CMPT 710 - Complexity Theory: Lecture 18, §3.1, pp. 3–4: split by the leading coefficient in the last variable]{ref}

The <algorithm> samples a point, performs exact <polynomial evaluation>, rejects the identity if the value is nonzero, and otherwise accepts. The lemma bounds false acceptance for every fixed nonzero <input>. For the <polynomial identity testing over a finite field> example, $G$ has $d=2$ and $|S|=5$, so its exact $2/5$ error attains the bound. Numerical near-zero values from <floating-point arithmetic> do not satisfy this exact algebraic contract. A <polynomial-time algorithm> claim additionally needs efficient sampling and evaluation, including the <bit> cost of representing and operating on <field> elements. Counting <field> operations alone does not establish that cost.

= Independent repetition of a polynomial identity test
{parent=Polynomial identity testing}
{title2=$p_k=p_1^k\le(d/|S|)^k\quad(d<|S|)$}

Repeat the <random evaluation test for a polynomial identity> with fresh <independent random variables>, keeping the same fixed <polynomial>. Reject as soon as any <polynomial evaluation> is nonzero; accept only if all $k$ values vanish. An identity is always accepted, preserving <one-sided error>. If a nonzero <polynomial> has single-trial false acceptance <probability> $p_1$, <independence> gives $p_k=p_1^k$. The <Schwartz-Zippel lemma> bounds this by $(d/|S|)^k$ when $d<|S|$.

For $G(x)=(x-1)(x-2)$ over the <finite field> $\mathbb F_5$, two uniform <independent> choices $(a,b)$ have $25$ equally likely ordered outcomes, each with <probability> $1/25$. Both <polynomial evaluations> are zero only at $(1,1),(1,2),(2,1),(2,2)$. Hence false acceptance falls from $2/5$ in one trial to $4/25$ in two trials, and correct rejection rises from $3/5$ to $21/25$.

If the second choice reuses the first, the pair is $(a,a)$ and only five diagonal outcomes are possible. Two still falsely accept, so the error remains $2/5$. Choosing fresh <independent> points is precisely what makes the full $25$-cell grid and the product of <probabilities> valid. For a target error $0<\varepsilon<1$, this example needs
$$
k\ge\left\lceil\frac{\log(1/\varepsilon)}{\log(5/2)}\right\rceil.
$$
The <ceiling function> makes the trial count an <integer>. Four trials give $(2/5)^4=16/625>1/100$, while six give $64/15625<1/100$; five still give $32/3125>1/100$, so six is the first count below one percent. This is an exact error guarantee for each run on $G$, rather than an observed success rate.
